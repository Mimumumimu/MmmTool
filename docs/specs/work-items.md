# 作業管理

作業を木構造で管理し、日ごとの実績と備考を残す機能 (WBS の入力画面)。サイドバーのページ 1 つと、設定ページのオン・オフ ([settings.md](settings.md))。`src/Plugins/MmmTool.WorkItems/`(Core 側は `src/Plugins/MmmTool.WorkItems.Core/`)。フォルダ名を `Tasks` にしないのは、`System.Threading.Tasks` を隠すため。

カレンダー型の画面 (ガントチャート)は、この機能に含めない。別の画面として、別に設計する (入力する表と、日付を横に並べて見る表示は、操作も内容も違い、混ぜると入力が遅くなるため。行の高さを固定にし、日付を行が持つ形にしてあるので、作るときにこの画面を直さなくてよい)。

**仮の決定**: 本文で「(仮)」と付けたものは、実装のときに実装者が仮に決めたもので、ユーザーが確認するまで仮。画面の文言 (ダイアログのタイトル・削除の確認文・エラーの文・「新しい作業」など)も、すべて仮。決まったら「(仮)」を外す。

## 目的と使い方
- 案件・区分・作業を、段数に制限のない木構造で持つ。表の 1 列目が木構造、右の列が入力欄で、1 画面に収める
- 毎日の入力は、**入力日** (左上。既定は当日)の実績と日の備考。ほかの項目は、作ったときと変えたときだけ触る
- 気軽に入れられることを優先する。別画面を開かず、表のセルに直接入力する。必須の入力は、名前だけ

## 行の種類
| 種類 | 内容 |
| --- | --- |
| 案件 | 案件マスターの 1 件 (表 `WorkProject`)。一番上の行。入力するのは名前と備考だけ。日付・進捗度・予定時間・実績は、下の作業から計算して表示する |
| グループ | 案件やグループの下に置く、子を持つ行 (区分など。表 `WorkGroup`)。入力するのは名前と備考だけ。計算して表示するものは案件と同じ |
| 作業 | 入力する行 (表 `WorkItem`)。案件かグループの下に置く。子を持たない |

- 案件・グループ・作業は、種類ごとに別の表に持つ
  - 案件をグループの一種にしない: 案件は選ぶ対象で、権限や独自の属性が付く独立したもの。同じ表に入れると、行が自分の番号を `ProjectId` に持つ作りになり、グループを最上位へ動かすと案件が増える
  - グループと作業を別の表にする (ユーザーの決定。1 つの表に種類を持たせる方式とは、性能・整合性が引き分けだった): 作業の列 (状態・予定など)に本物の値が入り、グループの行に意味のない既定値が入らない
- 種類は、作ったときに決める (案件は「案件の管理」の画面で追加し、グループと作業はメニューの「グループを追加」「作業を追加」)。あとから変えない (グループを案件にする、作業をグループにする、といった変換は無い。入力した値のある作業に子を足すと、その値を集計に混ぜるか消すかの例外が増えるため。グループの値は常に子からの計算、作業の値は常に入力、の 1 通りにする)。作業の下に子が欲しくなったときは、新しいグループを作り、その作業を移動する
- 案件の中身は、グループ・作業のどちらでもよい。グループの中身も同じ。段数に上限は無い
- 兄弟の並びは、保存した順 (`SortOrder`)。グループと作業は、同じ親の下で混ざって並ぶので、2 つの表にまたがる 1 つの数で順番を決める。「上へ」「下へ」で入れ替える。案件の並びは、名前の順 (仮。「上へ」「下へ」は、グループと作業だけ)
- 追加した行の名前は、「新しい案件」「新しいグループ」「新しい作業」(仮)。名前は必須で、空の名前を作らないため、初期の名前を入れてから、名前の入力欄へフォーカスを移す (全体が選ばれるので、そのまま打ち替えられる)
- **案件の見た目**: 名前を太字・アクセント色で出し、入れ子のグループ (やや太字)と見分ける。案件の追加は、ページ見出し右の「案件の管理」から (一覧の空いたところの右クリックでは作らない。案件は全員で共有するマスターなので、誤操作で増やさない)。案件・グループの中の追加は、その行を右クリックして選ぶ (仮)。画面に出す案件は、利用者が選んだものだけ (下の「表示する案件」)
- 行の識別は、「種類 + 番号」 (表ごとに番号が別の連番なので、案件 3 とグループ 3 と作業 3 が重なりうる)
- エラーの InfoBar は、画面を押し下げず、表の上に重ねて出す

## 項目
### 作業の項目 (作業ごとの共通の値)
| 項目 | 型 | 既定値 | 内容 |
| --- | --- | --- | --- |
| 名前 | 文字列 (200) | (入力) | 必須。案件・グループと共通 |
| 担当者 | ユーザーの番号 (`AppUser.Id`。0 は未割り当て) | 作った人 | 1 つの作業に 1 人。表の「担当」の列のセルを押すと、ユーザーの一覧のメニューが出て、選ぶとその場で保存する (並びは、先頭が「未割り当て」、次が自分、そのあとが表示名の順)(仮。ユーザーが増えたら、検索して選ぶ形に直す)。ローカルモードは、ユーザーが 1 人 (固定のローカルユーザー) だけなので、担当の列と「自分の担当だけ」は出さない (値は保存する)。作成者 (`CreatedByUserId`)とは別の列 (作成者は記録用で、機能には使わない)。グループ・案件には持たない |
| 優先度 | 高 / 中 / 低 | 中 | Backlog と同じ 3 段階。コードマスタから選ぶ (区分 3。下の「コードマスタ」)。保存するのは、コード番号 |
| 開始日・期限日 | 日付 | なし | 開始日 ≦ 期限日。逆のときは保存せず、理由を InfoBar に出す |
| 状態 | 未対応 / 作業予定 / 作業中 / 完了 | 未対応 | 4 つ (「処理済み」は持たない。「作業予定」は、作業報告の予定を取り出す手がかり。[work-report.md](work-report.md))。コードマスタから選ぶ (区分 1)。保存するのは、コード番号。Backlog と連携するときの対応は、そのとき決める |
| 進捗度 | コード番号 | 1 (0%) | コードマスタから選ぶ (区分 2。下の「コードマスタ」)。保存するのは、コード番号 (% の数値は、コードマスタの数値から引く) |
| 予定時間 | 時間 (小数可。0 以上 9999 以下) | なし | 作業ごとの共通の値。日ごとにしない (日ごとの実績と意味が重なるため。1 つなら、実績の合計との比較と、グループの進捗度の重み付けに使える) |
| リンク | 文字列 (2000) | 空 | URL・フォルダ・ファイルのパスを 1 つ。案件・グループにもある。下の「リンク」 |
| 備考 | 文字列 (1000) | 空 | 作業ごとの共通の備考 (永続)。グループにもある |
| 完了日 | 日付 | なし | 状態が完了に変わった入力日。画面の「完了日」の列に出す (入力できない表示だけ)。編集もしない。状態が完了のときだけ意味を持つ。作業だけが持つ (案件・グループの完了は、下の作業から求める。上の「完了したグループを畳む」) |
| 実績の累計 | 時間 | 0 | その作業の、全員の、すべての日の実績の合計。内部の値 (下の「実績 (累計)」) |

### 日ごとの記録 (作業 × 日付)
| 項目 | 型 | 内容 |
| --- | --- | --- |
| 実績 | 時間 (小数可) | その日にかけた時間。0 以上 24 以下。小数 2 桁に丸める |
| 日の備考 | 文字列 (1000) | その日の備考 |

- 1 つの作業の 1 日につき、**1 件** (人は区別しない)。担当者は 1 人なので、ほかの人が入れても代行入力で、同じ 1 件を直す。同じ日に何度直しても、1 件のまま。表の「実績 (日)」「備考 (日)」の入力欄は、その 1 件。最後に書いた内容が残る (同時編集の上書きは検出しない。下の「データ」)
- 実績と日の備考が両方とも空・0 になったら、その記録は論理削除する。同じ日に入れ直したときは、その行を使い回す (同じ日の行を増やさない)
- 作業の**実績 (累計)** は、その作業の全員の、すべての日の実績の合計。表示だけで、入力はできない。値は作業の行が持ち (`ActualTotalHours`)、記録を保存するとき、同じトランザクションで、その作業の記録をすべて足し直して書く (差分は足さない)。表を開くたびに、記録の表を集計しないため。正は記録の行で、作業の行の値は読み出しを速くするための写し (上の「実績の累計の更新」)
- 記録が作業ごと・日ごとに 1 件なので、作業の行の「実績 (日)」も、案件・グループの合計も、その日の全部の記録を出す

### 日報メモ (入力日ごと・人ごと。作業に結びつかない)
打ち合わせなど、作業に結びつかないその日の記入を、1 日に 1 つ書ける。作業の「備考」「備考 (日)」は、作業に付く付け足しなので、別の言葉にした。
- 名前を「備考」にしない: 「備考」は何かに付ける付け足しの意味で、作業に付かない 1 日分の記入とは、粒度も持ち主も違う。同じ言葉が 3 つの意味になると、画面でも会話でも取り違える
- 作業の日の備考 (`WorkRecord.Note`)に混ぜない: 作業の記録は作業に属し (案件の番号で絞って読む・累計を計算し直す)、日報メモは作業にも案件にも属さない
- 空にしても論理削除しない: 1 人 1 日 1 行までしか増えず、消す理由が無いため (作業の日ごとの記録は、累計と行の数を抑えるため、空になると論理削除する)。作業報告は、空と、行が無いことを区別しない
- 持ち方: 1 人 1 日 1 件 (表 `WorkDayNote`。持ち主は業務の列 `UserId`)。型は文字列 (2000)。空にしたときは、行を残して空文字にする (論理削除しない)。ほかの人のメモは読まない (自分の分だけ)
- **画面**: ページの下 (表の下)に、複数行の入力欄を 1 つ置く。見出しは付けず、空のときの薄い文字を `2026/10/13 (火) の日報メモ` にして、どの日のメモかを示す (入力日に連動。曜日は PC の言語に依らず日本語)。毎日は書かないので、表の上のバーには置かない。高さは 5 行ぶんで固定、長いときは縦のスクロール。入力日を変えると、その日のメモに切り替わる
- **保存**: 入力欄のフォーカスが外れたときに、その場で保存する (表のセルと同じ。確認ボタンは無い)。空白だけにしたときは、空にする。2000 文字を超える入力は、入力欄が受け付けない。保存に失敗したときは、理由を InfoBar に出し、入力欄を保存されている値に戻す
- **差分の取得の対象外**: 日報メモは自分の分だけで、複数の端末で同じ人のデータを開く想定にしない。60 秒ごとの差分の取得で読まず (問い合わせの数を増やさない)、読むのは、最初の読み込みと、入力日を変えたときだけ
- **作業報告での使い方**: 報告日の分を「■予定」の末尾に、書いたとおり出す。「■実績」には出さない ([work-report.md](work-report.md))

### グループの計算 (表示のみ。`WorkItemTree`)
グループの下にある**作業すべて** (段数を問わない)から計算する。入力はできない。選んだ案件の中身はすべて読んでいるので、案件の行も含め、読んだ作業から Core (`WorkItemTree`)で計算する。保存はしない (上の「実績の累計の更新」)。
- 開始日: 子の開始日の最小 / 期限日: 子の期限日の最大 (入っている作業だけで求める。1 つも無ければ空)
- 予定時間: 合計 (予定時間の入った作業が 1 つも無ければ空)
- 実績 (日): 入力日の実績の合計
- 実績 (累計): 下の作業の実績の累計 (`ActualTotalHours`)の合計
- 進捗度: すべての作業に予定時間 (0 より大きい値)が入っているときは、予定時間で重みを付けた平均。そうでないときは、作業の件数の平均。整数に四捨五入する (10 刻みになるとは限らない)。作業が 1 つも無いグループは空
- 優先度・状態は、グループに出さない
- 親が見つからない行 (手で直したデータなど)は、その案件の直下に出す

### 実績の累計の更新
作業の**実績の累計** (`ActualTotalHours`)は、保存先に持つ値で、更新は次のとおり行う。
- 記録を保存したとき、同じトランザクションの中で、その作業の記録をすべて足して書く (差分は足さない)。1 つの作業の記録は、足しても 1 ミリ秒未満。前にずれがあっても、次の保存で直る。差分を足す形にしない (前のずれが残り続け、画面の値から出した差分だと、同時に書く人の変更を取りこぼすため)。DB に計算を任せる形 (SQL Server のインデックス付きビュー)は、SQLite に無く、仕組みが 2 つになるので使わない。MmmBatch に任せる形は、反映が次の実行まで遅れ、ローカルモードには MmmBatch が無く、止まると全員の合計が古くなるので採らない
- 計算の前に、その作業の行をロックする (SQL Server は `UPDLOCK`)。同時に同じ作業の記録を書く人がいても、足し直しの結果が食い違わないため
- 行の更新は、**変えた列だけ書く**。画面が持っている古い値で、他の人が書いた列 (実績の累計など)を消さないため
- **案件・グループの合計は保存しない**。選んだ案件の中身は、すべて読むので、読んだ作業の値から Core (`WorkItemTree`)で足す。保存する値を増やすと、ずれる場所も増えるため
- 計算の部品は、Core に 1 つ置く。保存のときにアプリが呼び、保存先の実装 (SQLite・SQL Server)が違っても、同じ部品を呼ぶ。計算し直す形なので、どこで何度実行しても結果は同じ。MmmBatch に移す・足すときも、同じ部品を呼べる

### リンク
案件・グループ・作業の行に、リンクを 1 つ付けられる。同じ案件の Backlog の URL、仕様書のフォルダ、設計書のファイルなどを、行から開くために使う。
- 持ち方: 各行の列 `Link` (文字列。2000 文字まで。無いときは空文字)。複数のリンクは持たない (使い方が、行ごとに開きたい先 1 つのため。行の列なら、専用の表が要らず、読み込み・差分の取得・案件をまたぐ移動・削除が他の列と同じで済む。複数が要るときに専用の表を足し、この列は代表のリンクとして残せる)。案件の Backlog の URL は案件の行に付けると、作業ごとに同じ URL を貼らずに済む。作業の名前にリンクを付けない (名前のセルは、押すと入力に入る操作と、開く操作がぶつかるため)
- 表の「リンク」の列 (左の固定部分の、実績 (累計)の右隣): リンクがある行には、青い下線つきの「リンク」だけを出す (パスは出さない。ポイントすると出る)。無い行は空。列は「表示列」で隠せる
- **左クリック (フォーカスのあるセルで Enter)**: そのリンクを開く。リンクが無い行では何もしない。開けなかったときは、理由を InfoBar に出す
- **入れる・直す**: 行のどこを右クリックしても、メニューに「リンクを編集…」が出る。「リンク」の列の下に入力欄が開き (行の左端の下ではない。視線が離れないため。「リンク」の列が隠れているときは、メニューに出さない)、URL かパスを貼る。Enter か入力欄を閉じたときに保存する (Esc は取り消し)。空にして確定すると、リンクを空にする
- **クリア**: 「リンク」のセルを右クリックしたときだけ、メニューに「リンクをクリア」が出る (行の別の所では出さない。押し間違いで消さないため)。リンクの中身だけを空にする (行は残る)。確認のダイアログは出さない (「日付をクリア」と同じ)。リンクが無い行では、押せない。「削除」でなく「クリア」にしたのは、行を残して中身だけを空にする操作のため (文言の用語集)
- 開く処理は、SDK の `IPathOpener` (リンクの機能と同じ)。URL・フォルダ・ファイル・実行ファイル・独自スキームを、種類を問わずそのまま開く。**DB モードでも検査しない**。DB モードでは、他の人が登録したリンクを開くことになる。リンクの機能が検査しないとした根拠は、`Links.json` を自分しか書き込めないことだったが、ここは他の人が登録した文字列も開く。実行ファイルや独自スキームを他の人が仕込める点は、利用者が承知のうえの仕様
- 更新できる人の判定は、名前・備考と同じ (`IWorkItemEditPolicy`)

### 自分の担当だけ
上のバーのトグルスイッチ「自分の担当だけ」。オンのときは、自分が担当の作業の行だけを出す。**グループ・案件の集計 (日付・予定・実績・進捗度・状態)は、全員の作業から計算したまま変えない** (案件・グループの進捗は「全体の進み具合」で、見る人によって数字が変わらないようにする)。自分だけの進捗は、必要になったら、別に足す。既定はオフで、この PC の設定に残す (`WorkItems.MineOnly`。真偽)。絞り込みは、読み込んだあとにメモリで行う。読み込みの時点で絞ると、他の人が担当を変えた作業が、差分の取得で届かず、古いまま残るため。自分の担当が 1 件も無いグループは、空のグループとして残す (消すと、作ったばかりのグループが見えなくなるため。合計は、全員の分が出る)。ローカルモードでは、トグルを出さず、絞り込みもしない。

### 表示する案件
- 案件は、全員で共有する一覧 (案件マスター。表 `WorkProject`)。画面に出すのは、**全部の案件から、利用者が表示しないと決めた案件を除いたもの** (最初は全部表示する。新しく作られた案件も、自動で出る)。表示しない案件の番号は、**この PC の設定**に持つ (`Data/AppSettings.json`。PC ごとに違ってよい。Teams などの、チーム内の全部の案件が並んで、自分で非表示にする使い方と同じ)。別の PC では、非表示にし直す。表の案件の右クリックに「非表示にする」を足さない (表示する案件は、「案件の管理」で選ぶ)
- 選んだ案件は、広げて出す。三角で閉じられる (開閉の状態は保存しない。下の「案件・グループの開閉」)
- 表示している案件が 1 つも無いとき (すべて非表示にしたときなど)は、一覧の位置に「表示する案件を選んでください」(仮)と案内を出す
- 案件を新しく作ったとき (案件の管理の画面)は、作った人の選択に自動で加える
- 案件・グループは全員で共有する構造なので、ユーザーで絞らない (画面に出す案件を選ぶのは見え方の選択で、権限ではない)。実績の累計も、全員の合計。最初から自分の分だけに絞る前提で作ると、共有に広げるときに、読み込み・集計・表の作り直しになるため
- 案件を、最初は閉じた状態で全件出す形にしない (閉じた案件の行にも合計を出すには、案件の合計の保存と再計算が要り、ずれる場所が増える)。完了した案件を自動で非表示にしない (完了は読むたびに計算する値で、作業を足すと未完了に戻るのに、非表示のまま残るため)
- 表示しない案件を DB の表に持たない: 利点は、どの PC でも同じ案件が並ぶことと、読むときに結合で絞れることだが、前者は要件にせず、後者は番号を 1 つの JSON で渡して `ProjectId` で除く形で同じ性能になる。案件が増えて読む量が増える (進行中の案件が 5,000 件なら約 75 万行を、開くたびに全員が読む)のは、承知のうえ
- 保存先のモードを切り替える (設定の保存先を変えて保存する)と、この設定は消す (`IDatabaseModeChangeHandler`。ユーザー設定なので消えてよい。全部の案件が表示に戻る)。削除された案件の番号が残っても、読み込みに影響しない。案件を追加したとき、この設定は変えない
- 選ぶ画面と、案件を登録する画面は、下の「画面」の「表示する案件を選ぶ」「案件の管理」

### 完了したグループを畳む
一覧が長くなり続けないよう、完了して日がたった作業は、既定で隠す (下の「完了の表示」)。「完了」を「表示」にしたときは、中身がすべて完了して日がたったグループを、既定で畳んで 1 行で出す (下の「グループの既定の開閉」)。**案件の行は、完了しても隠さない** (案件を出し入れするのは「表示する案件」。完了は計算値で、作業を足すと未完了に戻るため)。グループの行は、「完了」が「非表示」のときだけ隠す。
- **完了日** (作業): 状態が完了に変わったとき、そのときの入力日を完了日に入れる。完了から外れたときは消す (ない日 = `9999-12-31`)。画面からは直せない。入力日が過去のときに完了にすると、完了日も過去になる (その日付で入力した、という意味)
- **未完了の作業**: 状態が完了でない作業、または完了日が `9999-12-31` の作業。状態が正で、完了日があっても、状態が完了でなければ、完了日は無視する (次にその行を保存するときに消す)。状態が完了なのに完了日が無い行 (手で直したデータなど)は、未完了として扱い、隠さない
- **グループの完了**: 下に作業が 1 件以上あり、未完了の作業が 1 件も無いとき、完了とする。完了日は、下の作業の完了日の最大値。作業が 1 件も無いグループは、完了にしない (作ったばかりのグループが消えないため)。選んだ案件の中身はすべて読んでいるので、Core で計算する (保存しない)
- **案件の完了**: 案件を隠すためではなく、選ぶ画面と管理画面に「完了」の印を出すために、読むときに計算する (作業が 1 件以上あり、未完了の作業が 1 件も無い)。保存しない
- **案件・グループの状態** (入力できない計算値): 下の作業がすべて未対応なら「未対応」、すべて完了なら「完了」、それ以外は「作業中」。下に作業が無ければ空。保存しない。進捗度と同じく、青い文字で出す
- **読み込み**: 選んだ案件の中身は、完了した行も含めて、すべて読む (日付にも依存しない)
- **グループの既定の開閉**: 「グループの完了」で、完了日が入力日より前のグループは、既定で畳む。入力日と比べるのは、入力日を過去に戻したとき、その日に動いていたグループを開いて出すため (「過去の日は、入力日を動かして見る」と合う)。下に、作業が 1 件も無いグループ (空)があるときは、畳まない (空のグループが、親と一緒に見えなくなるのを防ぐため)。行は消えず、三角を押せば、中のグループと作業がすべて出る。利用者が開いた・閉じたグループは、その状態を保つ (画面の中だけ。保存しない)。**入力日を変えたら、開閉の記録は捨てて、既定からやり直す** (昨日開いたグループが、今日も開いたまま残ると、完了した作業が見えて分かりにくいため)。作業を足すとグループは未完了に戻るので、広げて出る。作業が 1 件も無いグループは完了にしないので、畳まない。三角は、中身が 1 つも無い (作業も子のグループも無い)グループだけ出さない

### 完了の表示
完了した作業の見え方を、上のバーのコンボボックス「完了」で選ぶ。ツールチップは「入力日に完了した作業は、常に表示します」。選択肢の名前は、選んだあとに画面に残るものを表す。

| 選択肢 | 作業の行 (完了日が入力日より前) | すべて完了したグループ |
|---|---|---|
| 表示 | 出す | 今までどおり。既定で畳む (上の「グループの既定の開閉」) |
| グループのみ表示 (既定) | 隠す | 残す。中の作業がすべて隠れたときは、三角を出さない |
| 非表示 | 隠す | 隠す |

- **置き場所と並び**: 上のバーの右側で、「表示する案件」→「自分の担当だけ」→「完了」の順 (広い範囲を決めるものから、中を絞るものへ、左から右)
- **保存**: しない。起動のたびに、既定の「グループのみ表示」へ戻る
- **隠す条件**: 作業は `WorkSummary.IsFinishedBefore(入力日)`。入力日に完了した作業は、「グループのみ表示」「非表示」でも出す (押し間違いに気づけるように。今日やったことが見えるように)。グループは、「グループの既定の開閉」で畳む条件と同じ (完了日が入力日より前。下に作業が 1 件も無いグループがあるときは、隠さない)
- **案件の行**: 隠さない。中の作業がすべて隠れても、案件の行は出る (案件の出し入れは「表示する案件」で行い、2 つの隠し方を同じ行に持たせない)
- **集計**: 変えない。隠した作業も、案件・グループの合計・進捗度・状態に入る
- **ほかの絞り込みとの関係**: 「自分の担当だけ」とは重ねて効く。絞り込みは、読み込んだあとにメモリで行う
- **ローカルモード**: 「自分の担当だけ」と違い、出す
- 「非表示」で隠れたグループには、作業を追加できない (追加するときは、「グループのみ表示」か「表示」に切り替える。人が決めた区分を自動で消さずに済む選択肢を、別に用意してあるため)

### 完了して日がたった作業は触れない
完了した作業が、翌日以降も表に残り続けるので (完了しても隠さない)、終わったことが見た目で分かり、うっかり触れないようにする。

仕様:
- **対象**: 作業の行のうち、**完了日が入力日より前**のもの (`WorkSummary.IsFinishedBefore(入力日)`。「グループの既定の開閉」と同じ条件)。完了と同じ日の作業は、触れる (完了にしたのを、同じ日に直せるように)
- **触れなくするもの**: その行のすべてのセルの入力 (名前・担当・優先度・開始日・期限日・状態・進捗度・実績 (日)・備考 (日)・備考)と、右クリックのメニューの操作
- **見た目**: 触れなくなった行だけを、背景の灰色で出す (完了と同じ日の作業は、灰色にしない)。文字は薄くしない (読みやすさの基準のコントラスト比 4.5 倍を守る値にすると、通常の文字とほぼ変わらず、空のときの入力の手がかりの薄い文字と紛らわしいため)。

設計:
- 案件・グループは対象にしない (計算値の行で、すでに畳まれる)
- 右クリックのメニューで止める項目は、「上へ」「下へ」「移動…」「削除…」「日付をクリア」「リンクを編集…」「リンクをクリア」。「作業を追加」は、触れない行の兄弟として足すだけで、その行を変えないので、使える (止めると、触れない行の隣に新しい作業を足したいとき、追加できなくなる)
- リンクのセルを押して開くことと、備考・備考 (日)のセルを押して全文を読むことはできる (備考の入力欄は読み取り専用で、閉じても保存しない。備考が空の行は、読むものがないので、開かない)
- 直し方は、入力日を完了日に戻す (「過去の日は、入力日を動かして見る」と同じ操作)。専用の「再開」の操作は足さない (足すと、触れないことの意味が薄れるため)
- 灰色は、行の背景に重ねる半透明の色 (SDK の `ITreeGridRow.RowTint`。案件の青い背景と同じ仕組み)で出す。文字の色は変えない。入力の手がかり (「時間 (H)」)は、触れない行には出さない
- 止める場所は画面だけ (行の `CanEdit`・ViewModel の更新の入口・右クリックのメニュー・備考の入力欄)。サービス・保存先は止めない。更新の判定 `IWorkItemEditPolicy` とは別
- 止めないもの: 触れる隣の行の「上へ」「下へ」で、触れない行の位置が入れ替わる。触れない行を含むグループの「移動…」「削除…」で、中の触れない作業も動く・消える。別の PC・別の人からの更新

### 期限切れの表示
未完了の作業で、期限日が過ぎているものを、期限日のセルで知らせる。

- **対象**: 作業の行のうち、未完了 (`WorkSummary.IsFinished` が false)で、期限日が**入力日より前**のもの (`WorkSummary.OverdueDays(入力日)`。期限日の当日は、過ぎていない)。入力日と比べるのは、「完了して日がたった作業は触れない」「グループの既定の開閉」と同じ基準にそろえ、入力日を過去に戻したとき、その日に遅れていた作業が出るため。完了した作業は、期限を過ぎてから完了したものも含めて、印を出さない
- **見た目**: 期限日の文字を、テーマ標準の危険の色 (`SystemFillColorCriticalBrush`。ライト・ダーク・ハイコントラストに追従)にし、右に警告のアイコン (Segoe Fluent Icons の `E7BA`・14px)を付ける。アイコンに触れると、「3 日超過」のように過ぎた日数を出す。色だけで伝えないためにアイコンも付ける。列の幅は広げない (期限日の列は、編集のカレンダーのボタンの分の余白があり、表示のときはそこに収まる)
- 状態と進捗度の食い違いの警告 (黄の注意の色)と色が違うのは、あれが入力への注意で、こちらが遅れの続く状態だから
- 案件・グループの行には出さない (期限日は下の作業の最大値で、下の作業の 1 つが期限切れでもグループの日付は先のことがあり、赤くすると読み違える)。炎の絵文字は使わない (フォントで見え方が変わり、Fluent の画面から浮く)。行やセルの背景色・吹き出し・`InfoBar` は使わない (背景は入力できるセルの色・行の色と区別しにくく、吹き出しなどは入力直後に一度だけ出す知らせで、続く状態に合わない)

### 状態と進捗度・実績の食い違いの警告
状態と進捗度は連動させず (Backlog も独立している。「外部レビュー完了」(90)の次の 100 が、状態の完了と一致するとは限らない。連動させると、一方を直したときに、もう一方が意図せず変わる)、食い違う入力も保存する。入力を禁止する案 (「未対応のあいだは進捗・実績を入力できない」「進捗 100% でないと完了にできない」)は採らない (始めた日に状態を変え忘れると、実績が入れられず、作業報告の手がかりも欠ける。進捗度は 10% 刻みで、90% のまま終わる作業もある)。毎日の入力の気軽さを守るため、保存は止めず、入力した直後に、食い違いを短く知らせる。
- **条件** (作業の行だけ。案件・グループは計算値なので出さない。判定は Core の `WorkItemWarnings.Check`)

  | 入力した直後 | 警告の文 |
  | --- | --- |
  | 状態を「完了」にしたとき、進捗度が 100% ではない | 進捗度が 100% ではありません。 |
  | 状態が「未対応」の行に、進捗度 (0% より大きい)を入れた | 状態が「未対応」です。 |
  | 状態が「未対応」の行に、実績 (日。0 より大きい)を入れた | 状態が「未対応」です。 |
  | 入力日が開始日より前の行に、実績 (日。0 より大きい)か備考 (日。空ではない)を入れた | 入力日が開始日より前です。 |

  - 上の 3 つの入力以外では、出さない。状態を「未対応」にしたとき (選んだ状態を言い直すだけになる)と、「完了」の行の進捗度を下げたときは、出さない
  - 「作業予定」「作業中」の行には、状態の食い違いの警告を出さない
  - 開始日より前の警告は、開始日が空の行には出さない。進捗度を選んだときは出さない (ユーザーの決定)。同時に「未対応」の警告が当てはまるときは、「未対応」を出す (吹き出しは 1 つ)
- **タイミング**: 上の入力を保存できた直後。保存できなかったとき (入力の誤り)は、エラーだけを出す。前から食い違っている行は、開き直しても何も出ない (入力のときだけ知らせる)
- **見た目**: 入力したセルの下に、小さな吹き出し (SDK の `WarningBubble`。警告のアイコンと文)を出す。色はテーマの標準の注意の色 (`SystemFillColorCaution`・`SystemFillColorCautionBackground`)で、ライト・ダーク・ハイコントラストに追従する。約 4 秒でフェードして消え、次のクリック・キー操作でも、すぐ消える。フォーカスを取らず、クリックも受けないので、そのまま次のセルへ進める。列の幅は変えない (セルの中には、何も足さない。セルの中に印を足すと、最小にしたい列の幅が広がる。画面上部の `InfoBar` は、入力したセルから視線が離れる。セルの背景色は、入力できるセルの薄い色・行の色と区別しにくい)
- 保存するものは無い (設定・DB の列は増えない)。ViewModel が、保存の成功のあとに `WarningRaised` を発火し、ページが、行と列のキーからセルを引いて (`TreeGridView.FindCell`)吹き出しを出す

### 変更の履歴は持たない
作業の項目を変えても、変更前の値は残さない (最後の値だけを持つ)。日ごとの記録 (実績・日の備考)は、入力日の分を表で見る。過去の日は、入力日を動かして見る。変更の証拠が要る種類のデータではなく、履歴を持つと、変更の検出・記録の表・右のペインの画面が増えて、変更前の値を見返す場面に対して部品が多すぎるため、右のペインも持たない。

## コードマスタ
状態・進捗度・優先度の選択肢は、コードマスタ (表 `CodeMaster`。全員で共通)に集める。作業の行は**コード番号**を保存し、名前は表から引く (名前を直す・選択肢を足す・並べ替えるときに、保存済みの作業を書き換えなくて済む。進捗度の % を表の数値に置くので、10 刻みに固定せず、55% のような値も、行を足すだけで選べる)。

- 列: 機能番号 (`FeatureNo`)・区分番号 (`CategoryNo`)・コード番号 (`CodeNo`)・表示順 (`SortOrder`)・数値 (`NumericValue`)・名前 (`Name`。100 文字まで)。(`FeatureNo`, `CategoryNo`, `CodeNo`) で 1 件が決まる
- **機能番号**は、機能の名前や並びが変わっても変えない数字 (文字のキーにすると、名前を直すときに、コードと DB の両方を直すことになるため)。台帳は `MmmTool.CodeMaster.Core` の `CodeFeatures` (作業管理は 2。ほかの機能は、使うときに足す)。区分番号とコード番号の割り当ては、その機能の Core が決める (作業管理は `WorkCodes`)
- 作業管理の区分は、1 = 状態、2 = 進捗度、3 = 優先度
- 初期値は次のとおり (作成スクリプトが入れる。作成者・更新者は、SQL Server が 0、SQLite が 1)

  | 区分 | コード番号 | 表示順 | 数値 | 名前 |
  | --- | --- | --- | --- | --- |
  | 1 状態 | 1 | 1 | 0 | 未対応 |
  | 1 状態 | 2 | 2 | 0 | 作業予定 |
  | 1 状態 | 3 | 3 | 0 | 作業中 |
  | 1 状態 | 4 | 4 | 0 | 完了 |
  | 2 進捗度 | 1 | 1 | 0 | (空) |
  | 2 進捗度 | 2 | 2 | 10 | (空) |
  | 2 進捗度 | 3 | 3 | 20 | (空) |
  | 2 進捗度 | 4 | 4 | 30 | (空) |
  | 2 進捗度 | 5 | 5 | 40 | (空) |
  | 2 進捗度 | 6 | 6 | 50 | (空) |
  | 2 進捗度 | 7 | 7 | 60 | (空) |
  | 2 進捗度 | 8 | 8 | 70 | 作成完了 |
  | 2 進捗度 | 9 | 9 | 80 | 内部レビュー完了 |
  | 2 進捗度 | 10 | 10 | 90 | 外部レビュー完了 |
  | 2 進捗度 | 11 | 11 | 100 | (空) |
  | 3 優先度 | 1 | 1 | 0 | 高 |
  | 3 優先度 | 2 | 2 | 0 | 中 |
  | 3 優先度 | 3 | 3 | 0 | 低 |

- **作業の行が保存するもの**: 状態・優先度・進捗度とも、コード番号 (`StatusCodeNo`・`PriorityCodeNo`・`ProgressCodeNo`)。進捗度の % は、コードマスタの数値から引く。例: 作業中を選べば 2、進捗度の 0% を選べば 1、100% を選べば 11 を保存する
- **コードが見分ける値**: 状態と優先度のコード番号は、コードの列挙 (`WorkItemStatus`・`WorkItemPriority`)の値と同じ。「完了」を見分ける処理 (完了日の記録・完了したグループを畳む・案件の完了の計算・案件・グループの状態の計算)が、コード番号 4 (`WorkItemStatus.Closed`)に頼るため、状態のコード番号は変えない。表が持つのは、名前と表示順
- **画面の表記**: 状態・優先度は名前のまま。進捗度は `{数値}% ({名前})`、名前が空なら `{数値}%`。名前に % を入れない (数値が正で、名前は説明だけ。数値を直しても、表記がずれない)。グループの進捗度 (計算値)は、同じ数値の選択肢に名前があれば、その名前を付ける
- **選択肢を足す・並べ替える**: 行を足して、表示順を振り直す (例: 55% を足すときは、数値 55・新しいコード番号 12・表示順 7 の行を足す)。作業の行はコード番号だけを持つので、書き換えない。一度使ったコード番号を、別の意味に使わない
- **選択肢を外す**: 物理的に消さず、論理削除する (`IsDeleted` = 1)。選択肢の一覧から外れるが、その番号を持つ過去の作業は、名前を引ける。同じコード番号で戻せる
- **編集は、画面から行わない** (ローカルモードも同じ)。全員に影響し、アプリにユーザー・権限の区別が無いため。管理は別ツールの責務 (まだ無い)。直すときは、DB の表を SQL で直す
- 保存先は、ローカルモードが SQLite (`Data/MmmTool.db`)、DB モードが SQL Server の表 `CodeMaster`。読み込みで、作業管理の機能番号の全件 (論理削除を含む)を読み、差分の取得でも、更新された行が届く

## 画面 (`Main/WorkItemPage` ＋ `WorkItemViewModel` ＋ `WorkItemRow`)
- 余白 24・タイトル「作業管理」。リンク・クリップボード転送のページと同じ作り。結果・エラーは、ページ上部の InfoBar に出す (次の操作の成功で消える)
- 上のバー: 左端に **入力日**: 「◀」「▶」(前日・翌日)・日付 (`CalendarDatePicker`。既定は当日。曜日つきで `2026/10/13 (火)` の形。曜日は PC の言語に依らず日本語。表の開始日・期限日・完了日には曜日を付けない)・「今日」ボタン。右側に、「自分の担当だけ」(トグルスイッチ。上の「自分の担当だけ」。いつも切り替える操作なので、メニューに隠さず、バーに出す)・区切り線・「表示する案件」(仮。選ぶフライアウトを開く ▼付きのボタン。下の「表示する案件を選ぶ」)・「表示列」(▼付きのボタン)。トグルは、▼付きのボタン 2 つに挟まれると据わりが悪いので、左端に置き、区切り線で分ける。ページ見出し「作業管理」の右端に、「作業報告」([work-report.md](work-report.md))と「案件の管理」のボタンを置く (案件マスターの管理は、日々の操作ではないので、バーに混ぜない)。行の追加はボタンにせず、右クリックのメニューだけで行う (下の「右クリックのメニュー」)。主な操作は、日々の入力 (表のセルへの入力)なので、強調色のボタンは置かない
- 表 (SDK の `TreeGridView`。[SDK の controls.md](../../external/MmmSdk/docs/controls.md)):
  - **左の固定部分** (横にスクロールしない): 名前 (木構造。字下げ・開閉ボタン) / 担当 / 優先度 / 開始日 / 期限日 / 完了日 / 予定 (累計) / 実績 (累計) / リンク。あまり変えない項目と、積み上がった合計を、名前と一緒に見渡せるようにする
  - 予定の列の見出しは「予定 (累計)」(見出しは短くする。「実績 (累計)」と同じ書き方で、作業全体の予定であることを示す)。見出しに触れると「作業全体の予定の工数 (時間)」と説明を出す (SDK の `TreeGridColumn.HeaderToolTip`)。入力の手がかり (空の欄の薄い文字)は、予定・実績 (日)とも「時間 (H)」
  - **右の列 (毎日入力する列)** (横にスクロールする): 状態 / 進捗度 / 実績 (日) / 備考 (日) / 備考。改行を含む長い文が入る備考を後ろに置く。最後の「備考」は作業ごとの共通の備考で、これも毎日入力する扱い
  - **毎日入力する列は、見出しの下の緑の線で区別する** (背景は塗らない。ダークテーマで、入力欄全体の緑が重く見えたため。線の色は、ページのリソース `DailyLineBrush` で、明るい・暗いの 2 組)。「どこに入れればよいか」を迷わないための印で、説明の文言は付けない。優先度を左の固定部分に置くのは、緑の列を 1 つの連続した帯にして、区別を分かりやすくするため。SDK の `TreeGridColumn.HeaderUnderline` で付ける
  - 見出しは「実績 (日)」「備考 (日)」(入力日の分であることは、緑の線と上の入力日で分かる。日付は見出しに入れない)。日付を持たない共通の備考は「備考」
  - セルは、普段は文字だけを出し (表示用)、入力するときだけ、そのセルが入力欄に切り替わる (入力用。文字・時間: `TextBox`、日付: `CalendarDatePicker`)。優先度・状態・進捗度は、入力欄に切り替えず、クリックで選択肢のメニューを、セルの下に出す (今の値にチェック)。入力に入るのは、左クリックと、フォーカスのあるセルで Enter を押したとき。右クリックでは入らない (メニューだけが出る)。カレンダーは、切り替わるとすぐ開く (1 回のクリックで選べる)。入力を確定したとき (フォーカスが外れたとき・Enter・入力中のセルの外を押したとき。行の中の入力できないセルや、ほかの行でも同じ)に、その場で保存し、表示用に戻る。確認ボタンは無い。入力欄にフォーカスが入ったら、全体を選ぶ。グループの行の計算値のセルは、入力に入らない。入力できるセルは、触れると薄く色が付く
    - 日付は、カレンダーの選択欄 (`CalendarDatePicker`。表示は `2026/10/10`)で選ぶ。日付をクリアするときは、日付のセルを右クリックして「日付をクリア」(作業の開始日・期限日のセルだけに出る)。日付が選ばれたとき (確定)に保存し、行の値と同じなら何もしない (表の行は使い回されるので、日付の変更のイベントは、使い回しの差し替えでも起きるため)。Delete・Backspace キーで日付を消す案は採らない (カレンダーが開いている間は、キーが入力欄に届かず効かないため)
    - IME は、入力欄の入力スコープ (`InputScope`)で決める。日本語を入れる欄 (名前・備考)は `Hiragana`、時間 (予定時間・実績)は `Number`。コードでフォーカスのたびにオン・オフを切り替えない (入力欄にフォーカスが入った時点で、入力の仕組み (TSF)が IME の状態を初期化し、先にコードでオンにしても上書きされるため。入力スコープは、その初期化が読む正式な指定。タイマーで何度も設定し直す方法は、タイミングへの依存なので採らない)
    - 時間は、`NumberBox` ではなく数字の文字で入れる (仮。空は、なし。実績の空は 0)
    - 優先度・状態・進捗度は、メニューの項目が選ばれたときに、行の値と比べて、変わっていれば保存する
    - 全セルに入力欄を常に置かない (右クリックでも入力欄にフォーカスが入り、全選択・IME・「×」が一瞬動き、外から止められない。1 行に入力欄・カレンダーが十数個あって重い)。表の標準 (DataGrid や表計算)にならう
    - 入力欄の変更のイベント (選択が変わった・文字が変わった)で保存しない。行の使い回しの差し替えで値が変わるたびに起き、別の行の値が保存される事故の元になる。確定の操作 (フォーカスが外れた・Enter)でだけ保存し、画面の値が行の今の値と同じなら何もしない
    - 優先度・状態・進捗度に `ComboBox` を使わない (行の中で、一覧の項目を選べなかった。原因は特定できていない。行ごとに置くと重い)。メニューは、右クリックのメニューで動作が確かめられている
  - グループ (案件を含む)の行は、右のスクロールする部分の背景を、左の固定の部分と同じ暗い色にする (計算値の行を、入力欄が並ぶ作業の行と見分けるため)
  - 実績 (累計)は、作業・グループとも入力できない。グループの行の計算列は、入力できず、青系の色 (リソース `GroupTextBrush`)で出す。グループの名前も同じ色で、やや太字。案件は、グループと見分けるため、より濃い青 (リソース `ProjectTextBrush`)の太字で、文字も一回り大きく (16。ほかは 14。18 は大きすぎ、14 は物足りない)、行全体に、グループの行より濃い青の背景 (半透明。`ITreeGridRow.RowTint`)を重ねる (仮。橙・琥珀は警告色に見えるので避けた。薄い灰色や太字、アクセント色への連動は、入力の手がかりと区別できない・ライトで紺になって見分けにくいため、固定の色にした。案件とグループは、濃さの差だけでは、目を凝らさないと分からないため、色相・大きさ・背景で差を付けた)
  - 備考・備考 (日)は、セルに先頭の 1 行 (2 行以上あるときは「 …」つき)を出す (行の高さは固定)。押すと、セルの下に複数行の入力欄が開き、閉じたときに保存する
  - **作業の行の背景** (ダークも、ライトと同じ見え方にそろえる): 左の固定の列は、薄い同系色 (リソース `InputRowBackgroundBrush`)。右のスクロールする列は、SDK の表の面の色 (見出し・固定の列と同じ系統。`TreeGridPanelBackgroundBrush`)で、このページは色を渡さない (ページのカード背景にすると、暗い表示で見出しの色と食い違うため)。備考 (グループ・案件の行でも入力できる列)も、同じ色にそろえる (`KeepsBaseBackground`)
  - 行の高さは固定 (36)
  - 列の幅は、見出しと、表に出ている行の文字 (優先度・状態・進捗度は、メニューの選択肢ではなく、各行の表示) のうち、いちばん長いものに余白を足した幅に、自動で合わせる (備考だけ上限 320 で、超える分は「…」で省略)。行を追加・入力を確定したときに測り直す。測り直しでは、セルを作り直さない (入力中のフォーカスを保つため。SDK の `RefreshColumnWidths`)
  - 追加した作業の開始日は、今日になる (期限日は空)
  - 実績の入力欄は、空のとき薄い文字 (無効時の文字色)で「時間 (H)」と出す
  - 入力中の欄の右クリックは、行のメニューを出す (入力欄の「切り取り・コピー・貼り付け」のメニューは出ない。キー操作の Ctrl+X/C/V は使える)
  - 行の中を押した (左・右クリック)行・行の中の入力欄にフォーカスが入った行が、選んだ行になる (全部の行とも、行の上下の紫の線 (1px。セルのフォーカスの枠と同じ細さ)の枠だけで示す。背景の色は変えない。案件・グループの青い背景と、触れない行の灰色に、紫の背景を重ねると、色が混ざって、どちらの色か分からなくなるため。左端の細い縦線は、気づけないので使わない)
- 表示している案件が 1 つも無いときは、一覧の位置に「表示する案件を選んでください」(仮)と案内を出す。案件そのものが 1 つも無いとき (案件マスターが空)は、「「案件の管理」から、案件を追加してください」(仮)と案内を出す。表示している案件はあるが、中に作業が無いときは、案件の行だけを出す
- 表の下に、日報メモの入力欄を置く (上の「日報メモ」。見出し・ボタンは付けない)。ページの行は、見出し・バー・表・日報メモの順。表が残りの高さを使い、日報メモは 5 行ぶんの高さで固定

### 表示する案件を選ぶ (フライアウト。仮)
- 上のバーの「表示する案件」(仮)ボタンで、フライアウトを開く。中身は、検索欄・「非表示の案件も表示」のチェック・案件の一覧 (チェックボックス。名前と、完了済みの案件の印)。「非表示の案件も表示」の既定はオフで、オフのときは、表示している案件だけを一覧に出す (完了した案件も出る。外したい案件が、そのまま見つかるため)。オンにすると、非表示の案件も加わり、表示している案件を先頭にまとめる。フライアウトを開くたびに、オフへ戻す。表示中の案件が 0 件で、検索語が空のときの案内は、「表示中の案件がありません。「非表示の案件も表示」で、非表示の案件を出せます」(検索の結果が 0 件のときは、「該当する案件がありません」)。続きを読む位置は、オンのときに並びが入れ替わる分だけ前にずらし、すでに出ている案件は重ねて足さない (オフのときは、外した行が一覧から消えるので、ずれない)。案件の管理を開くボタンは、フライアウトの中には置かない (ページ見出し右に「案件の管理」があるため)
- チェックは、その案件を表示するか (入っていれば表示。最初は全部入っている)。入れる・外すと、その場で設定に保存し (確認ボタンは無い)、画面の案件を出し入れする。外しても、案件とその中身は消えない (画面から消えるだけ)
- 一覧は、数十件ずつ読む (終わりまでスクロールしたとき、続きを読む)。検索語は、名前の一部。「非表示の案件も表示」がオフのとき、チェックを外した案件は、その場で一覧から消える (非表示にした案件は、オンにするまで出さない)。戻すときは、オンにして、チェックを入れ直す。オンのときは、外した行は一覧に残る。「進行中のみ」は持たない (既定が進行中のみだと、案件がすべて完了したとき、完了した案件が一覧に出ず、外せなくなる。このフライアウトで外す相手は、表示中の案件。Teams の非表示のチームと同じ形)。
- 表示している案件は、一覧の先頭にまとめる (仮)

### 案件の管理 (ウィンドウ。仮)
- 案件マスター (全員で共有する案件の一覧)を、一覧で見て、登録・名前の変更・削除をする。一覧には、名前と、進行中か完了済みかを出す。検索欄は置かない (全件を続きの読み込みで出す。仮)。「進行中のみ」のチェックを持つ (既定はオン。選ぶ画面は持たない)
- 追加: 左上の強調色のボタン「＋ 新しい案件」(仮。送信先の一覧の「新規追加」と同じ形)を押すと、一覧の先頭に入力中の行が出て、名前の入力欄にフォーカスが移る。**Enter を押したときだけ**、確認ダイアログ (「案件の作成」。案件は全員で共有する一覧に加わる。仮)を出し、「作成」で保存する。フォーカスが外れただけでは保存しない (行は残り、続けて入力できる。案件は全員で共有するマスターなので、確定を緩くしない)。Esc か空のままなら、保存せずに行を消す (名前が空の案件は作らない)。保存したら一覧を読み直す。作った案件は、作った人の選択に加わる。名前の変更: 名前は、普段は文字だけで、クリックすると入力欄になる (作業管理の表と同じ)。フォーカスが外れたとき・Enter で保存し (Excel と同じ)、Esc で取り消す。削除: 行の右クリックのメニュー (文字の上でも出る)から。確認ダイアログを 2 回出し (1 回目は、中身も一緒に消えるので、消えるグループ・作業・日ごとの記録の件数つき。2 回目は「削除の最終確認」。全員の作業管理から消える。仮)、論理削除する ([削除](#削除)と同じ)
- 更新してよいかは、`IWorkItemEditPolicy` が決める (今は誰でも更新できる)
- 開く場所は、ページ見出し右の「案件の管理」だけ。大きさを変えられる (登録・名前の変更・削除は、一覧を検索しながら続けて行い、長くなることもあるため。表示する案件を選ぶ操作は、画面を見ながら何度も出入りさせるので、ほかの操作を止めないフライアウトにする。確認ボタンを持つダイアログは、そのたびに画面をふさぐ)

### 右クリックのメニュー
行の追加は、右クリックのメニューだけで行う。追加の位置は、右クリックした場所で決まる。
- **案件の行**: 「グループを追加」「作業を追加」(仮。案件の直下に、末尾として足す)。「上へ」「下へ」「移動…」「削除…」は出さない (案件の登録・名前の変更・削除は、案件の管理のウィンドウで行う)
- **グループの行**: 「グループを追加」「作業を追加」(仮。そのグループの子として末尾に足す。閉じていれば開く)
- **作業の行**: 「作業を追加」(仮。その作業と同じ親の下で、その作業の次に足す)。作業の下にグループを足す項目は、位置が分かりにくいので出さない
- **リンクのセル** (案件・グループ・作業とも。右クリックした所が「リンク」の列のとき): 「リンクを編集…」「リンクをクリア」(リンクが無い行では押せない)。上の追加の項目に続けて、区切り線のあとに出す
- **開始日・期限日のセル** (作業のみ): 「日付をクリア」。上の追加の項目に続けて、区切り線のあとに出す
- **一覧の空いたところ・見出し**: メニューなし (案件の追加はページ見出し右の「案件の管理」)
- グループと作業の行のメニューには、続けて次の項目を出す
  - 上へ / 下へ (同じ親の下の兄弟の中で入れ替える。先頭・末尾では無効)
  - 移動… (移動先のグループか案件を選ぶ。次の節)
  - 削除… (次の節)
- 追加した行は、名前が入力できる状態で出る
- 表のすべてのセル (入力できないセルも)が、フォーカスを受け、フォーカスのあるセルに白い枠が出る。Tab・Shift+Tab・矢印キーで、セルを、行と列の並びで移す (移ったセルは枠だけで、入力は始めない)。フォーカスのあるセルで Enter を押すと、入力・メニュー・カレンダー (備考は入力欄)が開く (メニューの列と備考は、Space でも開く)。Tab は枠を移すだけで、入力は始めない (仮。代わりに、入力できるセルへ Tab で移ったとき入力も始め、矢印キーは枠だけを移す形もある)。Esc は、どのセルでも、入力を取りやめる (入力欄・備考の入力欄とも、元の値に戻して閉じる。保存しない。枠はセルに残る)。キー操作 (Enter で行を追加する・Tab で字下げするなど)は、ほかには設けない (Excel のアウトラインの操作は、誤って階層が変わりやすい。メニューは、何が起こるかが文字で見え、行の種類も同じ場所で選べる)。

### 移動
- 選んだ行 (グループなら、中身ごと)を、別のグループの下か、選んでいる案件の直下へ移す。移動先は、木の一覧から選ぶ小さなダイアログ (「移動先を選択」。一覧は、選んでいる案件と、その中のグループ。選ぶと「移動」を押せる)。案件そのものは動かさない。グループを案件にする・案件をグループにする変換は無い。ドラッグ & ドロップは設けない
- 自分自身と、自分の中のグループへは移せない (一覧に出さない)。別の案件の下へも移せる (別の案件へ移すときは、移す行と、その作業の記録の案件の番号 (`ProjectId`)も直す。下の「データ」)。移したあとは、移動先の末尾に置く。移動先が閉じていれば開く

### 削除
- 確認ダイアログ (「削除の確認」)を出す。文言は、種類ごとに 1 行だけ: 「作業「名前」を削除します。」「グループ「名前」を削除します。」「案件「名前」を削除します。」。消える件数 (グループ・作業・日ごとの記録)は、出さない。案件の削除は、案件の管理のウィンドウで行い、確認を 2 回出す (1 回目は上の文言、2 回目は「削除の最終確認」。全員の作業管理から消える)
- 論理削除 (`IsDeleted`)だけを行う。完全削除 (物理削除)は、ローカルモード・DB モードとも行わない ([database.md](database.md))。削除した行は、画面に出さない

### 列の表示・非表示
- 設定ページまで行かず、この画面の中で切り替える (予定時間や進捗度は、入力が面倒になると使われなくなり、設定ページまで行く操作では切り替えが続かないため)。上のバーの「表示列」ボタンで、列の一覧 (チェック付き)を出す。続けて何列も切り替えられるよう、メニューではなく、開いたままの入れ物にする。名前の列は常に出す
- 非表示にした列の値は、消えない (見えないだけ。計算にも、そのまま使う)。保存先は設定ストア (`WorkItems.HiddenColumns`。列のキーをカンマでつないだ文字列。この PC の設定。DB モードでも DB には置かない)
- 既定は、すべての列を出す

### 案件・グループの開閉
- 開閉の状態は、保存しない (ページを開き直すと、選んだ案件は、すべて広げて出す。例外: 「完了」が「表示」のとき、完了して日がたったグループは、既定で畳む。「完了したグループを畳む」の「グループの既定の開閉」)。開いている間は、画面の中だけで覚える (他の人の更新を取り込んでも保つ)

## データ
### 保存先 (`IWorkItemRepository`)
- **前提**: 多人数が、大量の案件・作業・記録を共有して使う。ローカルモードも、同じ前提で、同じ表と同じ読み書きの形にする (保存先の違いは、型と接続だけ)
- 保存先は、ローカルモードが SQLite (`Data/MmmTool.db`)、DB モードが SQL Server。どちらも下の「表」の同じ設計で、行の型と変換 (`MmmTool.Data`)を共有する。サーバーへのデータ移行は行わない。ローカルも SQLite にするのは、日々増える記録 (日ごとの実績)が、1 件を書くたびにファイル全体を書き直す JSON と相性が悪く、SQLite なら書き込みが 1 件単位で、DB モードと同じ表・同じ読み書きの形になるため (未リリースで移すデータが無いので、JSON は残さない)
- **読み (必要な分だけ `SELECT` する。表示しない案件を除く)**
  - `LoadVisibleAsync(表示しない案件の番号の一覧)`: 表示する案件 (全部の案件から、表示しない案件を除いたもの)の行 (`WorkProject`)と、その中のグループ (`WorkGroup`)と作業 (`WorkItem`)のすべてと、作業管理のコードマスタ。表ごとに別の `SELECT` で、1 回の往復で受け取る。どの `SELECT` も、表示しない案件の番号 (1 つの JSON の配列。SQL Server は `OPENJSON`、SQLite は `json_each`)を `ProjectId` で除くだけ (`NOT IN`)で、返すのは自分の表の列だけ (JOIN で親の列が子の行に重なって届かない)。番号を 1 つずつパラメーターに並べると、数に上限があり、問い合わせの形も変わるので、何件でも同じ問い合わせになる JSON にした。木は、受け取ったあとにメモリで組み立てる。ユーザーで絞らない (表示する案件の中身は、全員の分)。「自分の担当だけ」は、読み込みのあとにメモリで絞る (上の「自分の担当だけ」)
  - `LoadDayAsync(入力日, 表示しない案件の番号の一覧)`: その日の記録 (全員分)。表示しない案件を除く (記録の行も `ProjectId` を持ち、同じ形で除く)
  - `LoadDayNoteAsync(入力日)`: その日の、自分の日報メモ (1 件。`(UserId, Date)` の一意の索引で引く)。入力日を変えたときと、最初の読み込みで呼ぶ
  - `SearchProjectsAsync(検索語, 進行中のみ, 表示中のみ, 表示しない案件の番号の一覧, 表示している案件を先頭に, 読み始める位置, 件数)`: 案件マスターの一覧 (案件の選択画面と管理画面で使う)。名前・表示しているか・完了済みか・完了日を返す。完了は読むときに計算する (作業が 1 件以上あり、未完了の作業が 1 件も無い)。数十件ずつ読む
  - `LoadProjectsAsync(案件の番号の一覧)`: 案件を番号で指定して、中身を読む (選びに加えた案件・案件の行が変わった案件の読み直し)
  - `UserId`・`RecoveryMessage`: 今のユーザーの番号 (SQLite は 1、SQL Server は `CurrentUser`)と、壊れたファイルを退避したときのメッセージ
  - 読み込みと差分の取得の問い合わせは、複数の `SELECT` を 1 つのコマンドで送り、結果を順に読む (1 回の往復)
  - `GetChangesAsync(基準の時刻, 入力日)`: 基準の時刻より後に更新された行 (下の「他の人の更新の反映」)
  - 実績の累計は作業の行が持つので、記録を集計して読まない
- **日付を変えたとき**: 入力日の記録だけを読み直し、日付をキーにした一覧 (`DateOnly` → その日の記録)の中身を上書きする。案件とその中身は、日付に依存しないので、読み直さない
- **書き (1 件単位の操作)**: 種類ごとに、追加・更新・論理削除の操作を持つ (`AddGroupAsync`・`UpdateItemAsync` など)。更新は、変えた列だけ書く
  - `SetDayNoteAsync(日付, メモ)`: 自分の日報メモを保存する。同じ (持ち主, 日付)の行があれば書き直し (更新が 0 行なら追加)、空にしても行は消さない。SQL Server は、別の PC との同時の書き込みで一意の索引に当たらないよう、更新に `UPDLOCK, HOLDLOCK` を付ける
  - `SetRecordAsync(記録)`: 記録を書き、同じトランザクションで、その作業の累計を計算し直す ([実績の累計の更新](#実績の累計の更新))。保存した記録と、計算し直した累計を返す
  - 案件を追加したとき (`AddProjectAsync`)は、同じトランザクションで、作った人の選択に加える
  - 並べ替え・移動は、動く行の `SortOrder` (グループと作業にまたがる 1 つの数)と親の番号を、まとめて書く (`UpdatePositionsAsync`)
  - 案件をまたぐ移動は、動かす行 (グループなら、その下のグループと作業)の `ProjectId` と、その作業の記録の `ProjectId` も、同じトランザクションで直す。移動元の案件の行 (`WorkProject`)の更新日時も更新する (移動元は、行が減ったことを、差分で知るため)
- 番号 (`Id`)は保存先が決める (`WorkRecord` は `bigint`、ほかは `int`)。表ごとに別の連番。グループの親は `ParentGroupId`、作業の親は `GroupId` で指す (どちらも 0 は案件の直下)。属する案件は、グループ・作業・記録の `ProjectId` で指す
- 入力の確認 (名前・日付・時間の範囲)・並べ替え・移動の位置の計算は、保存先ではなく、`WorkItemService`(Core。アプリ全体で 1 つ)が行う。保存に成功してから、メモリの内容を書き換えて `Changed` を発火する。操作は 1 つずつ順に行う
- 予測できる入力の誤りは、例外ではなく、画面に出せるメッセージで返す。保存の失敗は `DataFileException`
- 削除は論理削除だけ。**削除の印 (`IsDeleted`)は、選んだ行だけに付ける**。案件を削除したら案件の行 (`WorkProject`)だけ、グループを削除したらそのグループの行だけ、作業なら作業の行だけに付け、中のグループ・作業・日ごとの記録には付けない (消える件数は、確認ダイアログに出すために数える)。印を付けた行 1 つを戻せば、中身もそのまま戻る (印を 0 にして、更新日時を更新すれば、差分で各 PC に届く)。読むときは、削除された行を除き、さらに、親 (案件・グループ)の行が無い行 (中の行)は、画面に出さない (サービスが、読み込みと差分の反映のたびに外す。`PruneOrphans`)
- **他の人の更新の反映 (ローカルモードと DB モードで同じ仕組み)**: サービスが、保存先ごとの実装に頼らず、1 か所で行う。ページを開いたとき読み込む。そのあと 60 秒ごとに、`GetChangesAsync` で、**基準の時刻より後に更新された行だけ**を読み、読み込み済みの内容に反映する (差分の取得)。対象は、選んだ案件・グループ・作業の行、表示中の日の記録、コードマスタ。返ってきた行は、種類と番号と更新日時で突き合わせて反映するので、同じ行が何度届いても、結果は変わらない。表の行は、差分だけ反映する (入力中のセルを壊さない。`Rebuild` と同じ)
  - 「3 つの表の最大の更新日時を比べて、変わったら全体を読み直す」形にしない (多数が使うと、誰かが必ず更新しているので、全員が毎分、全体を読み直す)。ローカルモードと DB モードで反映の仕組みを変えない (動きが食い違い、片方でしか見つからない不具合が出る)
  - 基準の時刻は、保存先が返した最大の更新日時 (PC の時計は使わない)。次の確認では、基準から 60 秒戻して読む (確定前だった更新の取りこぼしを避けるため)
  - 更新日時のインデックスは、**削除された行も含める** (論理削除は更新日時が変わるので、差分で削除も届く)。作業の累計を書くときも、その行の更新日時を更新する
  - 他の人が作った案件は、案件の行が差分で届き (まだ読み込んでいない案件の行)、その案件の中身を読み直して、そのまま表示する (`LoadProjectsAsync`)。表示しない案件の更新は、届かない。案件をまたぐ移動で行が減った場合は、移動元の案件の行の更新日時が変わるので、その案件の中身を読み直す
  - 60 秒は設定の値 (1 か所)で、縮めても動く。ただし、多数の PC が直接 DB につなぐ間は、問い合わせの数が増える。リアルタイムに近づけるときは、API を間に置いて、サーバーから変更を知らせる形にする ([database.md](database.md) の「公開版は API 方式」)。呼び出しの単位 (選んだ案件ごと・差分の取得)は、API の後ろに移しても変えずに済む形にしてある
- **更新できる人**: 更新してよいかの判定を、サービスの更新の入口の 1 か所 (`IWorkItemEditPolicy`)に集める。今は、誰でも更新できる (`AnyoneCanEdit`)。将来、担当者と、リーダー的な人だけが更新できる実装を足す (リーダーの持ち方は、SQL Server の実装のときに決める。担当者は作業の `AssigneeUserId`)。誰でも更新できる実装は、そのあとも残す
- 同じ行を複数の人が同時に直したときの上書きは、検出しない (作業は基本的に 1 人が担当し、同じ行を同時に直す運用が、ほぼ無いため)。行の更新は変えた列だけ書くので、別の列を直した変更は消さない。防ぐ必要が出たときは、表を変えずに、更新の SQL の条件に「更新日時が読んだときと同じ」を足す ([database.md](database.md) の「表の決まり」)

### 表 (ローカルモードの SQLite と、DB モードの SQL Server で同じ)
表の決まり (共通ヘッダー・NULL を使わない・論理削除・外部キーなし)と、型の対応は [database.md](database.md) に従う。型は DB に依存しない言い方で書き、SQL Server と SQLite での型は database.md の「型の対応」を見る。**列ごとの型・既定値・検査・インデックスを書いた表の定義書は、[database.md](database.md) の「列」の「作業管理の表 (5 つ)」**。下の表は、その要約。列は、1 列目の `Id` と共通ヘッダー 5 列のあとに並ぶ。

| 表 | 内容の列 |
| --- | --- |
| `WorkProject` | 案件マスター。`Name`(200)・`Link`(2000)・`Note`(1000) |
| `WorkGroup` | グループ。`ProjectId`・`ParentGroupId`(0 は案件の直下)・`SortOrder`・`Name`(200)・`Link`(2000)・`Note`(1000) |
| `WorkItem` | 作業。`ProjectId`・`GroupId`(0 は案件の直下)・`SortOrder`・`Name`(200)・`AssigneeUserId`(0 は未割り当て)・`PriorityCodeNo`・`StartDate`(ない日は `0001-01-01`)・`DueDate`(ない日は `9999-12-31`)・`CompletedDate`(未完了は `9999-12-31`)・`PlannedHours`(0 は予定なし)・`ActualTotalHours`(実績の累計)・`Link`(2000)・`StatusCodeNo`・`ProgressCodeNo`・`Note`(1000) |
| `WorkRecord` | 日ごとの記録。`ProjectId`・`WorkItemId`・`Date`・`Hours`・`Note`(1000)。`Id` は `bigint` |
| `WorkDayNote` | 日報メモ。`UserId`・`Date`・`Note`(2000)。1 人 1 日 1 件。案件に属さない (`ProjectId` は持たない) |
| `CodeMaster` | コードマスタ (状態・進捗度・優先度の選択肢など)。`FeatureNo`・`CategoryNo`・`CodeNo`・`SortOrder`・`NumericValue`・`Name`(100)。「コードマスタ」の節 |

- 時間の列 (`Hours`・`PlannedHours`・`ActualTotalHours`)は、実数 (小数 2 桁)で持つ。SQL Server は `decimal`、SQLite は `REAL`。合計は、書くたびに小数 2 桁へ丸める (`ROUND(SUM(…), 2)`)ので、SQLite の誤差が積み上がらない ([database.md](database.md) の「型の対応」)
- 作成者 (`CreatedByUserId`)は記録用で、検索・一意・結合には使わない。日ごとの記録は、作業ごと・日ごとに 1 件で、持ち主を持たない (人で絞るときは、作業の担当者 `WorkItem.AssigneeUserId` で絞る)。案件・グループ・作業の作成者は、担当者とは別
- **インデックス** (更新日時を含むものは、削除された行も含める。ほかは削除されていない行だけ)
  - `WorkProject`: `(UpdatedAt)`
  - `WorkGroup`: `(ProjectId, UpdatedAt)`(選んだ案件の中身の読み込み・差分)
  - `WorkItem`: `(ProjectId, UpdatedAt)`(同上)・`(ProjectId, CompletedDate)`(案件の完了の計算)
  - `WorkDayNote`: `(UserId, Date)` は**一意** (1 人 1 日 1 件。日付の範囲の読み込み・直近の日の検索にも使う)。差分用の索引は持たない (日報メモは差分の取得の対象外)
  - `WorkRecord`: `(WorkItemId, Date)` は**一意** (作業ごと・日ごとに 1 件。作業の累計の計算し直しにも使う)・`(ProjectId, Date)`(その日の記録)・`(ProjectId, UpdatedAt)`(差分)。記録にも `ProjectId` を持つのは、選んだ案件に絞って読み、差分で取るため (全案件の 1 日分は、10 万人 × 1 日 5 件なら 50 万行。作業の表との結合では、差分に要る `(ProjectId, UpdatedAt)` の索引が作れない)
  - `CodeMaster`: `(FeatureNo, CategoryNo, CodeNo)` は**一意** (論理削除された行も含めて)・`(FeatureNo, UpdatedAt)`(機能ごとの読み込み・差分)
- ローカルモードのユーザーは、`Id = 1` の固定値。`AppUser` の表は SQLite に作らず、共通ヘッダーの作成者・更新者の列と `UserId` に 1 を入れる (表の形は、DB モードと同じに保つ)。DB モードでは `AppUser.Id`
- 表の作成スクリプトは、SQLite が `src/Data/MmmTool.Data.Sqlite/Sql/`、SQL Server が `src/Data/MmmTool.Data.SqlServer/Sql/` の `001_CreateTables.sql` に持つ。ローカルの SQLite は、アプリが起動時に作成と版の更新をする。SQL Server は、アプリが表の有無を調べて知らせるだけ ([database.md](database.md))
- DB の行の型 (`MmmTool.Data` の `WorkItemRow` など。種類ごと)と、アプリの型 (`WorkItem` など)は別にする (リマインダーと同じ。日付なし・予定なしの変換もここで行う)。SQLite と SQL Server で共有する
- コードマスタは、画面から編集しない。直すときは SQL で直す (「コードマスタ」の節)。作業の `PriorityCodeNo`・`StatusCodeNo`・`ProgressCodeNo` の列は、コードマスタのコード番号を指す (外部キーは使わない。存在する番号かどうかは、アプリが検査する)
- 保存した値 (作業の累計)が、手で直した SQL などでずれたときは、管理者が SQL で作り直す (`Sql/` に置く `RebuildActualTotal.sql`。記録から計算し直す)。普段は、保存のたびに計算し直すので、使わない

## 仮の決定 (実装時に決めたもの)
- 案件の並びは、画面の木では名前の順 (現在の文化の並び)。選ぶ画面と管理画面は、保存先の並び (名前の順)。完全には一致しない場合がある
- 選ぶ画面と管理画面の 1 回に読む件数は 50、検索は入力が止まって 300 ミリ秒後
- 予定時間の 0 は予定なし (保存先の 0 と同じ。0 を入力しても、予定なしに戻る)
- 案件の完了の計算は、状態が完了でない、または完了日が無い作業を未完了とする (状態が正)。問い合わせは `CompletedDate` と `Status` の両方を見る
- 案件の行の更新日時は、案件の名前・備考の変更、案件をまたぐ移動 (移動元と移動先)で更新する。差分で受け取った案件の行が、持っている行と更新日時が違うときは、その案件の中身を読み直す (自分の変更が戻ってきたときも、読み直す)

## 構成
- `MmmTool.WorkItems.Core`: `WorkProject`・`WorkGroup`・`WorkItem`(作業)・`WorkRecord`・`WorkDayNote`・`WorkCodes`・`IWorkItemRepository`・`IWorkItemEditPolicy`・`WorkItemService`・`WorkItemTree` ほか。保存先の実装は持たない (Core に DB の依存を入れない)
- 保存先の実装: `MmmTool.Data` に行の型と変換 (`WorkItemRow` など)、`MmmTool.Data.Sqlite` に SQLite の実装、`MmmTool.Data.SqlServer` に SQL Server の実装。SDK の `MmmSdk.Db.Sqlite` に、ファイルの場所・開く・版の更新・壊れたファイルの扱いを置く ([database.md](database.md))
- `MmmTool.WorkItems`: `WorkItemsPlugin`(入口。機能のキー `WorkItems`・既定でオフ・サイドバーの並び順 2 (CLI補助の次))・`WorkItemStartup`(起動時の読み込み)・`Main/`(ページ・ViewModel・表の行)・`Move/`(移動先を選ぶダイアログ)・`ProjectPicker/`(表示する案件を選ぶフライアウトの ViewModel と一覧の 1 件)・`ProjectManager/`(案件の管理のウィンドウ・ViewModel・一覧の 1 件)
