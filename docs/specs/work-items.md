# 作業管理

作業を木構造で管理し、日ごとの実績と備考を残す機能 (WBS の入力画面)。サイドバーのページ 1 つと、設定ページのオン・オフ ([settings.md](settings.md))。`src/Plugins/MmmTool.WorkItems/`(Core 側は `src/Plugins/MmmTool.WorkItems.Core/`)。フォルダ名を `Tasks` にしないのは、`System.Threading.Tasks` を隠すため。

カレンダー型の画面 (ガントチャート)は、この機能に含めない。別の画面として、別に設計する。

**仮の決定 (ユーザー確認待ち)**: 設計の案から変えた点・案に無かった点を、実装のときに、実装者が仮に決めた。本文では「(仮)」を付けてある。画面の文言 (ダイアログのタイトル・削除の確認文・エラーの文・「新しい作業」など)も、すべて仮。決まったら、「(仮)」を外す。

**今の状態**: 保存は、下の「データ」の設計どおり (ローカルは SQLite、DB モードは SQL Server。表は同じ。全員の分を共有して見る。選んだ案件だけを読む)に実装した (2026-10-11)。JSON の保存は廃止した。ビルドは通り、SQLite の保存は、確認用のコンソール (サービスと SQLite の組み合わせ。追加・更新・記録と累計・同時書き込み・移動・検索・選び・差分・削除・コードマスタ・旧版からの移行・壊れたファイル・作り直しのスクリプト)で確かめた。SQL Server の保存は、表を作成し (`mimumu202511` の `MmmTool`)、案件・グループ・作業・日ごとの記録の保存と日付のクリアを、実機で確かめた (2026-10-11)。複数人での同時の更新・別の PC の更新の取り込み・`RebuildActualTotal.sql` は未確認。ローカルモード (SQLite)の画面は、ユーザーが実機で動かして確かめた (2026-10-11)。画面 (表・選ぶフライアウト・案件の管理のウィンドウ)は、実機で一度も動かしていない。状態・進捗度・優先度の選択肢を、コードマスタ (表 `CodeMaster`)に移した (2026-10-11。ビルドは MmmTool.slnx・MmmBatch.slnx とも通った。SQLite は確認用のコンソールと、デバッグ版のデータの移行で確かめた。SQL Server は、表を作成して保存を確かめた。画面は未確認)。

## 目的と使い方
- 案件・区分・作業を、段数に制限のない木構造で持つ。表の 1 列目が木構造、右の列が入力欄で、1 画面に収める
- 毎日の入力は、**入力日** (左上。既定は当日)の実績と日の備考。ほかの項目は、作ったときと変えたときだけ触る
- 気軽に入れられることを優先する。別画面を開かず、表のセルに直接入力する。必須の入力は、名前だけ

## 行の種類
| 種類 | 内容 |
| --- | --- |
| 案件 | 案件マスターの 1 件 (表 `WorkProject`)。一番上の行。入力するのは名前と備考だけ。日付・進捗度・予定時間・実績は、下の作業から計算して表示する |
| グループ | 案件やグループの下に置く、子を持つ行 (区分など。表 `WorkGroup`)。入力するのは名前と備考だけ。計算して表示するものは案件と同じ |
| 作業 | 入力する行 (表 `WorkItem`)。案件かグループの下に置く。子を持たない |

- 案件・グループ・作業は、別の表に持つ (理由は下の「決定の理由」)
- 種類は、作ったときに決める (案件は「案件の管理」の画面で追加し、グループと作業はメニューの「グループを追加」「作業を追加」)。あとから変えない (グループを案件にする、作業をグループにする、といった変換は無い)。作業の下に子が欲しくなったときは、新しいグループを作り、その作業を移動する
- 案件の中身は、グループ・作業のどちらでもよい。グループの中身も同じ。段数に上限は無い
- 兄弟の並びは、保存した順 (`SortOrder`)。グループと作業は、同じ親の下で混ざって並ぶので、2 つの表にまたがる 1 つの数で順番を決める。「上へ」「下へ」で入れ替える。案件の並びは、名前の順 (仮。「上へ」「下へ」は、グループと作業だけ)
- 追加した行の名前は、「新しい案件」「新しいグループ」「新しい作業」(仮)。名前は必須で、空の名前を作らないため、初期の名前を入れてから、名前の入力欄へフォーカスを移す (全体が選ばれるので、そのまま打ち替えられる)
- **案件の見た目**: 名前を太字・アクセント色で出し、入れ子のグループ (やや太字)と見分ける。案件の追加は、ページ見出し右の「案件の管理」から (一覧の空いたところの右クリックでは作らない。案件は全員で共有するマスターなので、誤操作で増やさない。2026-10-11)。案件・グループの中の追加は、その行を右クリックして選ぶ (仮・ユーザー指示 2026-10-10)。画面に出す案件は、利用者が選んだものだけ (下の「表示する案件」)
- 行の識別は、「種類 + 番号」 (表ごとに番号が別の連番なので、案件 3 とグループ 3 と作業 3 が重なりうる)
- エラーの InfoBar は、画面を押し下げず、表の上に重ねて出す

## 項目
### 作業の項目 (作業ごとの共通の値)
| 項目 | 型 | 既定値 | 内容 |
| --- | --- | --- | --- |
| 名前 | 文字列 (200) | (入力) | 必須。案件・グループと共通 |
| 優先度 | 高 / 中 / 低 | 中 | Backlog と同じ 3 段階。コードマスタから選ぶ (区分 3。下の「コードマスタ」)。保存するのは、コード番号 |
| 開始日・期限日 | 日付 | なし | 開始日 ≦ 期限日。逆のときは保存せず、理由を InfoBar に出す |
| 状態 | 未対応 / 作業中 / 完了 | 未対応 | 3 つ (「処理済み」は持たない。ユーザー決定 2026-10-11)。コードマスタから選ぶ (区分 1)。保存するのは、コード番号。Backlog と連携するときの対応は、そのとき決める |
| 進捗度 | コード番号 | 1 (0%) | コードマスタから選ぶ (区分 2。下の「コードマスタ」)。保存するのは、コード番号 (% の数値は、コードマスタの数値から引く) |
| 予定時間 | 時間 (小数可。0 以上 9999 以下) | なし | 作業ごとの共通の値。日ごとではない |
| 備考 | 文字列 (1000) | 空 | 作業ごとの共通の備考 (永続)。グループにもある |
| 完了日 | 日付 | なし | 状態が完了に変わった入力日。内部の値で、画面には出さず、編集もしない。状態が完了のときだけ意味を持つ。作業だけが持つ (案件・グループの完了は、下の作業から求める。下の「完了した行を隠す」) |
| 実績の累計 | 時間 | 0 | その作業の、全員の、すべての日の実績の合計。内部の値 (下の「実績 (累計)」) |

### 日ごとの記録 (作業 × 日付 × 人)
| 項目 | 型 | 内容 |
| --- | --- | --- |
| 実績 | 時間 (小数可) | その日にかけた時間。0 以上 24 以下。小数 2 桁に丸める |
| 日の備考 | 文字列 (1000) | その日の備考 |

- 1 つの作業の 1 日につき、人ごとに 1 件。同じ日に何度直しても、1 件のまま。表の「実績 (日)」「備考 (日)」の入力欄は、自分の記録
- 実績と日の備考が両方とも空・0 になったら、その記録は論理削除する。同じ日に入れ直したときは、その行を使い回す (同じ日の行を増やさない)
- 作業の**実績 (累計)** は、その作業の全員の、すべての日の実績の合計。表示だけで、入力はできない。値は作業の行が持ち (`ActualTotalHours`)、記録を保存するとき、同じトランザクションで、その作業の記録をすべて足し直して書く (差分は足さない)。表を開くたびに、記録の表を集計しないため。正は記録の行で、作業の行の値は読み出しを速くするための写し (上の「実績の累計の更新」)
- 作業の行の「実績 (日)」に他の人の分を出すかは、担当者の列と一緒に、SQL Server の実装のときに決める。今は、行も案件・グループの合計も、自分の記録だけを出す (仮。累計は全員の分)

### グループの計算 (表示のみ。`WorkItemTree`)
グループの下にある**作業すべて** (段数を問わない)から計算する。入力はできない。選んだ案件の中身はすべて読んでいるので、案件の行も含め、読んだ作業から Core (`WorkItemTree`)で計算する。保存はしない (上の「実績の累計の更新」)。
- 開始日: 子の開始日の最小 / 期限日: 子の期限日の最大 (入っている作業だけで求める。1 つも無ければ空)
- 予定時間: 合計 (予定時間の入った作業が 1 つも無ければ空)
- 実績 (日): 入力日の実績の合計
- 実績 (累計): 下の作業の実績の累計 (`ActualTotalHours`)の合計
- 進捗度: すべての作業に予定時間 (0 より大きい値)が入っているときは、予定時間で重みを付けた平均。そうでないときは、作業の件数の平均。整数に四捨五入する (10 刻みになるとは限らない)。作業が 1 つも無いグループは空
- 優先度・状態は、グループに出さない
- 親が見つからない行 (手で直したデータなど)は、その案件の直下に出す

### 実績の累計の更新
作業の**実績の累計** (`ActualTotalHours`)は、保存先に持つ値で、更新は次のとおり行う。
- 記録を保存したとき、同じトランザクションの中で、その作業の記録をすべて足して書く (差分は足さない)。1 つの作業の記録は、足しても 1 ミリ秒未満。前にずれがあっても、次の保存で直る
- 計算の前に、その作業の行をロックする (SQL Server は `UPDLOCK`)。同時に同じ作業の記録を書く人がいても、足し直しの結果が食い違わないため
- 行の更新は、**変えた列だけ書く**。画面が持っている古い値で、他の人が書いた列 (実績の累計など)を消さないため
- **案件・グループの合計は保存しない**。選んだ案件の中身は、すべて読むので、読んだ作業の値から Core (`WorkItemTree`)で足す。保存する値を増やすと、ずれる場所も増えるため
- 計算の部品は、Core に 1 つ置く。保存のときにアプリが呼び、保存先の実装 (SQLite・SQL Server)が違っても、同じ部品を呼ぶ。計算し直す形なので、どこで何度実行しても結果は同じ。MmmBatch に移す・足すときも、同じ部品を呼べる

### 表示する案件
- 案件は、全員で共有する一覧 (案件マスター。表 `WorkProject`)。画面に出すのは、利用者が**選んだ案件だけ**。選んだ案件は、保存先に持つ (表 `WorkProjectSelection`。ユーザーごと)。どの PC で開いても、同じ案件が並ぶ
- 選んだ案件は、広げて出す。三角で閉じられる (開閉の状態は保存しない。下の「案件・グループの開閉」)
- 選んでいる案件が 1 つも無いとき (初めて開いたときなど)は、一覧の位置に「表示する案件を選んでください」(仮)と案内を出す
- 案件を新しく作ったとき (案件の管理の画面)は、作った人の選択に自動で加える
- 選ぶ画面と、案件を登録する画面は、下の「画面」の「表示する案件を選ぶ」「案件の管理」

### 完了した行を隠す
一覧が長くなり続けないよう、選んだ案件の中の、完了して日がたった行を、既定で隠す。隠すのは**表示だけ**で、集計 (実績 (累計)・予定・進捗度・日付)は、隠した行も含んだまま変わらない。案件そのものは隠さない (出す案件は、利用者が選ぶ)。
- **完了日** (作業): 状態が完了に変わったとき、そのときの入力日を完了日に入れる。完了から外れたときは消す (ない日 = `9999-12-31`)。画面からは直せない。入力日が過去のときに完了にすると、完了日も過去になる (その日付で入力した、という意味)
- **未完了の作業**: 状態が完了でない作業、または完了日が `9999-12-31` の作業。状態が正で、完了日があっても、状態が完了でなければ、完了日は無視する (次にその行を保存するときに消す)。状態が完了なのに完了日が無い行 (手で直したデータなど)は、未完了として扱い、隠さない
- **グループの完了**: 下に作業が 1 件以上あり、未完了の作業が 1 件も無いとき、完了とする。完了日は、下の作業の完了日の最大値。作業が 1 件も無いグループは、完了にしない (作ったばかりのグループが消えないため)。選んだ案件の中身はすべて読んでいるので、Core で計算する (保存しない)
- **案件の完了**: 案件を隠すためではなく、選ぶ画面と管理画面に「完了」の印を出すために、読むときに計算する (作業が 1 件以上あり、未完了の作業が 1 件も無い)。保存しない
- **案件・グループの状態** (入力できない計算値。ユーザー決定 2026-10-11): 下の作業がすべて未対応なら「未対応」、すべて完了なら「完了」、それ以外は「作業中」。下に作業が無ければ空。保存しない。進捗度と同じく、青い文字で出す
- **隠す条件**: 完了日が**入力日より前**のとき、隠す。完了日と同じ日と、それより前の入力日では、出す。今日の日付ではなく入力日と比べるのは、入力日を過去に戻したとき、その日に動いていた行を出すため (「過去の日は、入力日を動かして見る」と合う)
- **読み込み**: 選んだ案件の中身は、完了した行も含めて、すべて読む (日付にも依存しない)。そのため、隠す・出すの切り替えで、読み直さない
- **隠した行を出す切り替え**: 上のバーに、トグルスイッチ「完了を表示」を 1 つ置く (仮。文言はユーザーの案)。既定はオフで、この PC の設定に残す (`WorkItems.ShowFinished`。真偽)

### 変更の履歴は持たない
作業の項目を変えても、変更前の値は残さない (最後の値だけを持つ)。日ごとの記録 (実績・日の備考)は、入力日の分を表で見る。過去の日は、入力日を動かして見る。理由は下の「決定の理由」。

## コードマスタ
状態・進捗度・優先度の選択肢は、コードマスタ (表 `CodeMaster`。全員で共通)に集める。作業の行は**コード番号**を保存し、名前は表から引く (ユーザー決定 2026-10-11)。

- 列: 機能番号 (`FeatureNo`)・区分番号 (`CategoryNo`)・コード番号 (`CodeNo`)・表示順 (`SortOrder`)・数値 (`NumericValue`)・名前 (`Name`。100 文字まで)。(`FeatureNo`, `CategoryNo`, `CodeNo`) で 1 件が決まる
- **機能番号**は、機能の名前や並びが変わっても変えない数字。台帳は `MmmTool.CodeMaster.Core` の `CodeFeatures` (作業管理は 2。ほかの機能は、使うときに足す)。区分番号とコード番号の割り当ては、その機能の Core が決める (作業管理は `WorkCodes`)
- 作業管理の区分は、1 = 状態、2 = 進捗度、3 = 優先度
- 初期値は次のとおり (作成スクリプトが入れる。作成者・更新者は、SQL Server が 0、SQLite が 1)

  | 区分 | コード番号 | 表示順 | 数値 | 名前 |
  | --- | --- | --- | --- | --- |
  | 1 状態 | 1 | 1 | 0 | 未対応 |
  | 1 状態 | 2 | 2 | 0 | 作業中 |
  | 1 状態 | 3 | 3 | 0 | 完了 |
  | 2 進捗度 | 1 | 1 | 0 | (空) |
  | 2 進捗度 | 2 | 2 | 10 | (空) |
  | 2 進捗度 | 3 | 3 | 20 | (空) |
  | 2 進捗度 | 4 | 4 | 30 | (空) |
  | 2 進捗度 | 5 | 5 | 40 | (空) |
  | 2 進捗度 | 6 | 6 | 50 | (空) |
  | 2 進捗度 | 7 | 7 | 60 | (空) |
  | 2 進捗度 | 8 | 8 | 70 | 作成完了 |
  | 2 進捗度 | 9 | 9 | 80 | 内部レビュー完了 |
  | 2 進捗度 | 10 | 10 | 90 | 外部レビュー完了 |
  | 2 進捗度 | 11 | 11 | 100 | (空) |
  | 3 優先度 | 1 | 1 | 0 | 高 |
  | 3 優先度 | 2 | 2 | 0 | 中 |
  | 3 優先度 | 3 | 3 | 0 | 低 |

- **作業の行が保存するもの**: 状態・優先度・進捗度とも、コード番号 (`StatusCodeNo`・`PriorityCodeNo`・`ProgressCodeNo`)。進捗度の % は、コードマスタの数値から引く。例: 作業中を選べば 2、進捗度の 0% を選べば 1、100% を選べば 11 を保存する
- **コードが見分ける値**: 状態と優先度のコード番号は、コードの列挙 (`WorkItemStatus`・`WorkItemPriority`)の値と同じ。「完了」を見分ける処理 (完了日の記録・完了した行を隠す・案件の完了の計算・案件・グループの状態の計算)が、コード番号 3 に頼るため、状態のコード番号は変えない。表が持つのは、名前と表示順
- **画面の表記**: 状態・優先度は名前のまま。進捗度は `{数値}% ({名前})`、名前が空なら `{数値}%`。名前に % を入れない (数値が正で、名前は説明だけ。数値を直しても、表記がずれない)。グループの進捗度 (計算値)は、同じ数値の選択肢に名前があれば、その名前を付ける
- **選択肢を足す・並べ替える**: 行を足して、表示順を振り直す (例: 55% を足すときは、数値 55・新しいコード番号 12・表示順 7 の行を足す)。作業の行はコード番号だけを持つので、書き換えない。一度使ったコード番号を、別の意味に使わない
- **選択肢を外す**: 物理的に消さず、論理削除する (`IsDeleted` = 1)。選択肢の一覧から外れるが、その番号を持つ過去の作業は、名前を引ける。同じコード番号で戻せる
- **編集は、画面から行わない** (ローカルモードも同じ。ユーザー決定 2026-10-11)。全員に影響し、アプリにユーザー・権限の区別が無いため。管理は別ツールの責務 (まだ無い)。直すときは、DB の表を SQL で直す。進捗度のラベルを編集していた「設定」ボタンとダイアログは廃止した
- 保存先は、ローカルモードが SQLite (`Data/MmmTool.db`)、DB モードが SQL Server の表 `CodeMaster`。読み込みで、作業管理の機能番号の全件 (論理削除を含む)を読み、差分の取得でも、更新された行が届く

## 画面 (`Main/WorkItemPage` ＋ `WorkItemViewModel` ＋ `WorkItemRow`)
- 余白 24・タイトル「作業管理」。リンク・クリップボード転送のページと同じ作り。結果・エラーは、ページ上部の InfoBar に出す (次の操作の成功で消える)
- 上のバー: 左端に **入力日**: 「◀」「▶」(前日・翌日)・日付 (`CalendarDatePicker`。既定は当日)・「今日」ボタン。右側に、「完了を表示」(トグルスイッチ。仮。上の「完了した行を隠す」。いつも切り替える操作なので、メニューに隠さず、バーに出す)・区切り線・「表示する案件」(仮。選ぶフライアウトを開く ▼付きのボタン。下の「表示する案件を選ぶ」)・「表示列」(▼付きのボタン)。トグルは、▼付きのボタン 2 つに挟まれると据わりが悪いので、左端に置き、区切り線で分ける (ユーザー指摘 2026-10-11)。ページ見出し「作業管理」の右端に、「案件の管理」のボタンを置く (案件マスターの管理は、日々の操作ではないので、バーに混ぜない。ユーザー決定 2026-10-11)。行の追加はボタンにせず、右クリックのメニューだけで行う (下の「右クリックのメニュー」)。主な操作は、日々の入力 (表のセルへの入力)なので、強調色のボタンは置かない
- 表 (SDK の `TreeGridView`。[SDK の controls.md](../../external/MmmSdk/docs/controls.md)):
  - **左の固定部分** (横にスクロールしない): 名前 (木構造。字下げ・開閉ボタン) / 優先度 / 開始日 / 期限日 / 予定 (累計) / 実績 (累計)。あまり変えない項目と、積み上がった合計を、名前と一緒に見渡せるようにする
  - 予定の列の見出しは「予定 (累計)」(見出しは短くする。「実績 (累計)」と同じ書き方で、作業全体の予定であることを示す)。見出しに触れると「作業全体の予定の工数 (時間)」と説明を出す (SDK の `TreeGridColumn.HeaderToolTip`)。入力の手がかり (空の欄の薄い文字)は、予定・実績 (日)とも「時間 (H)」
  - **右の列 (毎日入力する列)** (横にスクロールする): 状態 / 進捗度 / 実績 (日) / 備考 (日) / 備考。改行を含む長い文が入る備考を後ろに置く。最後の「備考」は作業ごとの共通の備考で、これも毎日入力する扱い
  - **毎日入力する列は、見出しの下の緑の線で区別する** (背景は塗らない。ダークテーマで、入力欄全体の緑が重く見えたため。線の色は、ページのリソース `DailyLineBrush` で、明るい・暗いの 2 組)。「どこに入れればよいか」を迷わないための印で、説明の文言は付けない。SDK の `TreeGridColumn.HeaderUnderline` で付ける
  - 見出しは「実績 (日)」「備考 (日)」(入力日の分であることは、緑の背景と上の入力日で分かる。日付は見出しに入れない)。日付を持たない共通の備考は「備考」
  - セルは、普段は文字だけを出し (表示用)、入力するときだけ、そのセルが入力欄に切り替わる (入力用。文字・時間: `TextBox`、日付: `CalendarDatePicker`)。優先度・状態・進捗度は、入力欄に切り替えず、クリックで選択肢のメニューを、セルの下に出す (今の値にチェック)。入力に入るのは、左クリックと、フォーカスのあるセルで Enter を押したとき。右クリックでは入らない (メニューだけが出る)。カレンダーは、切り替わるとすぐ開く (1 回のクリックで選べる)。入力を確定したとき (フォーカスが外れたとき・Enter・入力中のセルの外を押したとき。行の中の入力できないセルや、ほかの行でも同じ)に、その場で保存し、表示用に戻る。確認ボタンは無い。入力欄にフォーカスが入ったら、全体を選ぶ。グループの行の計算値のセルは、入力に入らない。入力できるセルは、触れると薄く色が付く
    - 日付は、カレンダーの選択欄 (`CalendarDatePicker`。表示は `2026/10/10`)で選ぶ。日付をクリアするときは、日付のセルを右クリックして「日付をクリア」(作業の開始日・期限日のセルだけに出る)。日付が選ばれたとき (確定)に保存し、行の値と同じなら何もしない。理由は下の「決定の理由」
    - IME は、入力欄の入力スコープ (`InputScope`)で決める。日本語を入れる欄 (名前・備考)は `Hiragana`、時間 (予定時間・実績)は `Number`。コードでフォーカスのたびにオン・オフを切り替えない (理由は下の「決定の理由」。実機で未確認)
    - 時間は、`NumberBox` ではなく数字の文字で入れる (仮。空は、なし。実績の空は 0)
    - 優先度・状態・進捗度は、メニューの項目が選ばれたときに、行の値と比べて、変わっていれば保存する
  - グループ (案件を含む)の行は、右のスクロールする部分の背景を、左の固定の部分と同じ暗い色にする (計算値の行を、入力欄が並ぶ作業の行と見分けるため)
  - 実績 (累計)は、作業・グループとも入力できない。グループの行の計算列は、入力できず、青系の色 (リソース `GroupTextBrush`。明るい表示 #0F6CBD・暗い表示 #7BBCFF)で出す。グループの名前も同じ色で、やや太字。案件は、グループと見分けるため、より濃い青 (リソース `ProjectTextBrush`。明るい表示 #0B4F8F・暗い表示 #B5D8FF)の太字で、文字も一回り大きく (16。ほかは 14。18 は大きすぎ、14 は物足りなかった)、行全体に、グループの行より濃い青の背景 (半透明。`ITreeGridRow.RowTint`)を重ねる。最初は、案件を紫にしていたが (橙・琥珀は警告色に見えるので避けた)、明るい表示の背景を青にそろえたあと、「紫も青に」と決めた (2026-10-10) (仮。薄い灰色や太字、アクセント色への連動は、入力の手がかりと区別できなかった・ライトで紺になって見分けにくかったため、固定の色にした。案件とグループが、濃さの差だけでは、目を凝らさないと分からなかったため、色相・大きさ・背景で差を付けた)
  - 備考・備考 (日)は、セルに先頭の 1 行 (2 行以上あるときは「 …」つき)を出す (行の高さは固定)。押すと、セルの下に複数行の入力欄が開き、閉じたときに保存する
  - 行の高さは固定 (36)
  - 列の幅は、見出しと、表に出ている行の文字 (優先度・状態・進捗度は、メニューの選択肢ではなく、各行の表示) のうち、いちばん長いものに余白を足した幅に、自動で合わせる (備考だけ上限 320 で、超える分は「…」で省略)。行を追加・入力を確定したときに測り直す。測り直しでは、セルを作り直さない (入力中のフォーカスを保つため。SDK の `RefreshColumnWidths`)
  - 追加した作業の開始日は、今日になる (期限日は空)
  - 実績の入力欄は、空のとき薄い文字 (無効時の文字色)で「時間 (H)」と出す
  - 入力中の欄の右クリックは、行のメニューを出す (入力欄の「切り取り・コピー・貼り付け」のメニューは出ない。キー操作の Ctrl+X/C/V は使える)
  - 行の中を押した (左・右クリック)行・行の中の入力欄にフォーカスが入った行が、選んだ行になる (背景を薄くし、左端に細い線を出す)
- 選んでいる案件が 1 つも無いときは、一覧の位置に「表示する案件を選んでください」(仮)と案内を出す。案件そのものが 1 つも無いとき (案件マスターが空)は、「「案件の管理」から、案件を追加してください」(仮)と案内を出す。選んだ案件はあるが、中に作業が無いときは、案件の行だけを出す

### 表示する案件を選ぶ (フライアウト。仮)
- 上のバーの「表示する案件」(仮)ボタンで、フライアウトを開く。中身は、検索欄・「進行中のみ」のチェック・案件の一覧 (チェックボックス。名前と、完了済みの案件の印)。案件の管理を開くボタンは、フライアウトの中には置かない (ページ見出し右に「案件の管理」があるため。ユーザー決定 2026-10-11)
- チェックを入れる・外すと、その場で保存し (確認ボタンは無い)、画面の案件を出し入れする。外しても、案件とその中身は消えない (画面から消えるだけ)
- 一覧は、数十件ずつ読む (終わりまでスクロールしたとき、続きを読む)。検索語は、名前の一部。「進行中のみ」の既定は、オン (完了した案件で一覧が埋まらないため。仮)
- 選んだ案件は、一覧の先頭にまとめる (仮)

### 案件の管理 (ウィンドウ。仮)
- 案件マスター (全員で共有する案件の一覧)を、一覧で見て、登録・名前の変更・削除をする。一覧には、名前と、進行中か完了済みかを出す。検索欄は置かない (全件を続きの読み込みで出す。仮・ユーザー決定 2026-10-11)。「進行中のみ」のチェックは、選ぶ画面と同じ
- 追加: 左上の強調色のボタン「＋ 新しい案件」(仮。送信先の一覧の「新規追加」と同じ形)を押すと、一覧の先頭に入力中の行が出て、名前の入力欄にフォーカスが移る。**Enter を押したときだけ**、確認ダイアログ (「案件の作成」。案件は全員で共有する一覧に加わる。仮)を出し、「作成」で保存する。フォーカスが外れただけでは保存しない (行は残り、続けて入力できる。案件は全員で共有するマスターなので、確定を緩くしない)。Esc か空のままなら、保存せずに行を消す (名前が空の案件は作らない)。保存したら一覧を読み直す。作った案件は、作った人の選択に加わる。名前の変更: 名前は、普段は文字だけで、クリックすると入力欄になる (作業管理の表と同じ)。フォーカスが外れたとき・Enter で保存し (Excel と同じ)、Esc で取り消す。削除: 行の右クリックのメニュー (文字の上でも出る)から。確認ダイアログを 2 回出し (1 回目は、中身も一緒に消えるので、消えるグループ・作業・日ごとの記録の件数つき。2 回目は「削除の最終確認」。全員の作業管理から消える。仮)、論理削除する ([削除](#削除)と同じ)
- 更新してよいかは、`IWorkItemEditPolicy` が決める (今は誰でも更新できる)
- 開く場所は、ページ見出し右の「案件の管理」だけ。大きさを変えられる。理由は「決定の理由」

### 右クリックのメニュー
行の追加は、右クリックのメニューだけで行う。追加の位置は、右クリックした場所で決まる。
- **案件の行**: 「グループを追加」「作業を追加」(仮。案件の直下に、末尾として足す)。「上へ」「下へ」「移動…」「削除…」は出さない (案件の登録・名前の変更・削除は、案件の管理のウィンドウで行う)
- **グループの行**: 「グループを追加」「作業を追加」(仮。そのグループの子として末尾に足す。閉じていれば開く)
- **作業の行**: 「作業を追加」(仮。その作業と同じ親の下で、その作業の次に足す)。作業の下にグループを足す項目は、位置が分かりにくいので出さない
- **一覧の空いたところ・見出し**: メニューなし (案件の追加はページ見出し右の「案件の管理」)
- グループと作業の行のメニューには、続けて次の項目を出す
  - 上へ / 下へ (同じ親の下の兄弟の中で入れ替える。先頭・末尾では無効)
  - 移動… (移動先のグループか案件を選ぶ。次の節)
  - 削除… (次の節)
- 追加した行は、名前が入力できる状態で出る
- 表のすべてのセル (入力できないセルも)が、フォーカスを受け、フォーカスのあるセルに白い枠が出る。Tab・Shift+Tab・矢印キーで、セルを、行と列の並びで移す (移ったセルは枠だけで、入力は始めない)。フォーカスのあるセルで Enter を押すと、入力・メニュー・カレンダー (備考は入力欄)が開く (メニューの列と備考は、Space でも開く)。Tab は枠を移すだけで、入力は始めない (仮。代わりに、入力できるセルへ Tab で移ったとき入力も始め、矢印キーは枠だけを移す形もある)。Esc は、どのセルでも、入力を取りやめる (入力欄・備考の入力欄とも、元の値に戻して閉じる。保存しない。枠はセルに残る)。キー操作 (Enter で行を追加する・Tab で字下げするなど)は、ほかには設けない。

### 移動
- 選んだ行 (グループなら、中身ごと)を、別のグループの下か、選んでいる案件の直下へ移す。移動先は、木の一覧から選ぶ小さなダイアログ (「移動先を選択」。一覧は、選んでいる案件と、その中のグループ。選ぶと「移動」を押せる)。案件そのものは動かさない。グループを案件にする・案件をグループにする変換は無い。ドラッグ & ドロップは設けない
- 自分自身と、自分の中のグループへは移せない (一覧に出さない)。別の案件の下へも移せる (別の案件へ移すときは、移す行と、その作業の記録の案件の番号 (`ProjectId`)も直す。下の「データ」)。移したあとは、移動先の末尾に置く。移動先が閉じていれば開く

### 削除
- 確認ダイアログ (「削除の確認」)を出す。案件とグループは、中身も画面から消えるので、その件数 (グループ・作業・日ごとの記録)を出す。案件の削除は、案件の管理のウィンドウで行い、確認を 2 回出す (1 回目は件数つき、2 回目は「削除の最終確認」)。作業は、消える日ごとの記録の件数を出す。記録の件数は、読み込んでいない記録も含むので、保存先に数えさせる (`CountRecordsAsync`)
- 論理削除 (`IsDeleted`)だけを行う。完全削除 (物理削除)は、ローカルモード・DB モードとも行わない (ユーザーの決定。[database.md](database.md))。削除した行は、画面に出さない

### 列の表示・非表示
- 設定ページまで行かず、この画面の中で切り替える。上のバーの「表示列」ボタンで、列の一覧 (チェック付き)を出す。続けて何列も切り替えられるよう、メニューではなく、開いたままの入れ物にする。名前の列は常に出す
- 非表示にした列の値は、消えない (見えないだけ。計算にも、そのまま使う)。保存先は設定ストア (`WorkItems.HiddenColumns`。列のキーをカンマでつないだ文字列。この PC の設定。DB モードでも DB には置かない)
- 既定は、すべての列を出す

### 案件・グループの開閉
- 開閉の状態は、保存しない (ページを開き直すと、選んだ案件は、すべて広げて出す。ユーザー決定 2026-10-11)。開いている間は、画面の中だけで覚える (他の人の更新を取り込んでも保つ)

## データ
### 保存先 (`IWorkItemRepository`)
- **前提**: 多人数が、大量の案件・作業・記録を共有して使う。ローカルモードも、同じ前提で、同じ表と同じ読み書きの形にする (保存先の違いは、型と接続だけ)
- 保存先は、ローカルモードが SQLite (`Data/MmmTool.db`)、DB モードが SQL Server。どちらも下の「表」の同じ設計で、行の型と変換 (`MmmTool.Data`)を共有する。JSON の保存 (`JsonWorkItemRepository`・`Data/WorkItems.json` など)は廃止した。サーバーへのデータ移行は行わない
- **読み (必要な分だけ `SELECT` する。利用者が選んだ案件で絞る)**
  - `LoadSelectedAsync()`: 自分が選んだ案件の行 (`WorkProject`)と、その中のグループ (`WorkGroup`)と作業 (`WorkItem`)のすべてと、作業管理のコードマスタ。表ごとに別の `SELECT` で、1 回の往復で受け取る。どの `SELECT` も、`WorkProjectSelection` を `ProjectId` で INNER JOIN して絞るだけで、返すのは自分の表の列だけ (JOIN で親の列が子の行に重なって届かない)。木は、受け取ったあとにメモリで組み立てる。ユーザーで絞らない (選んだ案件の中身は、全員の分)。「自分に絞る」は、担当者の列を決めるときに、読み込みの条件として足す
  - `LoadDayAsync(入力日)`: その日の記録 (全員分)。選んだ案件に絞る (記録の行も `ProjectId` を持ち、同じ JOIN で絞る。全案件の 1 日分を読むと、1 日の記録がすべて届くため)
  - `SearchProjectsAsync(検索語, 進行中のみ, 選んだ案件を先頭に, 読み始める位置, 件数)`: 案件マスターの一覧 (案件の選択画面と管理画面で使う)。名前・選んでいるか・完了済みか・完了日を返す。完了は読むときに計算する (作業が 1 件以上あり、未完了の作業が 1 件も無い)。数十件ずつ読む
  - `CountRecordsAsync`: 削除の確認に出す記録の件数 (消える行の記録を数える)
  - `GetProjectDeleteImpactAsync`: 案件を削除すると消える件数 (グループ・作業・記録。案件の管理の確認に出す。読み込んでいない案件も数える)
  - `LoadProjectsAsync(案件の番号の一覧)`: 案件を番号で指定して、中身を読む (別の PC で選んだ案件・案件の行が変わった案件の読み直し。少数の番号だけを渡す)
  - `UserId`・`RecoveryMessage`: 今のユーザーの番号 (SQLite は 1、SQL Server は `CurrentUser`)と、壊れたファイルを退避したときのメッセージ
  - 読み込みと差分の取得の問い合わせは、複数の `SELECT` を 1 つのコマンドで送り、結果を順に読む (1 回の往復)
  - `GetChangesAsync(基準の時刻, 入力日)`: 基準の時刻より後に更新された行 (下の「他の人の更新の反映」)
  - 実績の累計は作業の行が持つので、記録を集計して読まない
- **日付を変えたとき**: 入力日の記録だけを読み直し、日付をキーにした一覧 (`DateOnly` → その日の記録)の中身を上書きする。案件とその中身は、日付に依存しないので、読み直さない
- **書き (1 件単位の操作)**: 種類ごとに、追加・更新・論理削除の操作を持つ (`AddGroupAsync`・`UpdateItemAsync` など)。更新は、変えた列だけ書く
  - `SetRecordAsync(記録)`: 記録を書き、同じトランザクションで、その作業の累計を計算し直す ([実績の累計の更新](#実績の累計の更新))。保存した記録と、計算し直した累計を返す
  - `SetProjectSelectedAsync(案件の番号, 選ぶか)`: 選択の行を書く。外したら論理削除し、選び直したら同じ行を使い回す
  - 案件を追加したとき (`AddProjectAsync`)は、同じトランザクションで、作った人の選択に加える
  - 並べ替え・移動は、動く行の `SortOrder` (グループと作業にまたがる 1 つの数)と親の番号を、まとめて書く (`UpdatePositionsAsync`)
  - 案件をまたぐ移動は、動かす行 (グループなら、その下のグループと作業)の `ProjectId` と、その作業の記録の `ProjectId` も、同じトランザクションで直す。移動元の案件の行 (`WorkProject`)の更新日時も更新する (移動元は、行が減ったことを、差分で知るため)
- 番号 (`Id`)は保存先が決める (`WorkRecord` は `bigint`、ほかは `int`)。表ごとに別の連番。グループの親は `ParentGroupId`、作業の親は `GroupId` で指す (どちらも 0 は案件の直下)。属する案件は、グループ・作業・記録の `ProjectId` で指す
- 入力の確認 (名前・日付・時間の範囲)・並べ替え・移動の位置の計算は、保存先ではなく、`WorkItemService`(Core。アプリ全体で 1 つ)が行う。保存に成功してから、メモリの内容を書き換えて `Changed` を発火する。操作は 1 つずつ順に行う
- 予測できる入力の誤りは、例外ではなく、画面に出せるメッセージで返す。保存の失敗は `DataFileException`
- 削除は論理削除だけ。**削除の印 (`IsDeleted`)は、選んだ行だけに付ける** (ユーザー決定 2026-10-11)。案件を削除したら案件の行 (`WorkProject`)だけ、グループを削除したらそのグループの行だけ、作業なら作業の行だけに付け、中のグループ・作業・日ごとの記録には付けない (消える件数は、確認ダイアログに出すために数える)。印を付けた行 1 つを戻せば、中身もそのまま戻る (印を 0 にして、更新日時を更新すれば、差分で各 PC に届く)。読むときは、削除された行を除き、さらに、親 (案件・グループ)の行が無い行 (中の行)は、画面に出さない (サービスが、読み込みと差分の反映のたびに外す。`PruneOrphans`)
- **他の人の更新の反映 (ローカルモードと DB モードで同じ仕組み)**: サービスが、保存先ごとの実装に頼らず、1 か所で行う。ページを開いたとき読み込む。そのあと 60 秒ごとに、`GetChangesAsync` で、**基準の時刻より後に更新された行だけ**を読み、読み込み済みの内容に反映する (差分の取得)。対象は、選んだ案件・グループ・作業の行、表示中の日の記録、自分の選択の行 (別の PC で選びを変えたとき)、コードマスタ。返ってきた行は、種類と番号と更新日時で突き合わせて反映するので、同じ行が何度届いても、結果は変わらない。表の行は、差分だけ反映する (入力中のセルを壊さない。今の `Rebuild` と同じ)
  - 基準の時刻は、保存先が返した最大の更新日時 (PC の時計は使わない)。次の確認では、基準から 60 秒戻して読む (確定前だった更新の取りこぼしを避けるため)
  - 更新日時のインデックスは、**削除された行も含める** (論理削除は更新日時が変わるので、差分で削除も届く)。作業の累計を書くときも、その行の更新日時を更新する
  - 自分の選択が変わっていたときは、選んだ案件を読み直す (`LoadSelectedAsync`)。案件をまたぐ移動で行が減った場合は、移動元の案件の行の更新日時が変わるので、その案件の中身を読み直す
  - 60 秒は設定の値 (1 か所)で、縮めても動く。ただし、多数の PC が直接 DB につなぐ間は、問い合わせの数が増える。リアルタイムに近づけるときは、API を間に置いて、サーバーから変更を知らせる形にする ([database.md](database.md) の「公開版は API 方式」)。呼び出しの単位 (選んだ案件ごと・差分の取得)は、API の後ろに移しても変えずに済む形にしてある
- **更新できる人**: 更新してよいかの判定を、サービスの更新の入口の 1 か所 (`IWorkItemEditPolicy`)に集める。今は、誰でも更新できる (`AnyoneCanEdit`)。将来、担当者と、リーダー的な人だけが更新できる実装を足す (担当者の列・リーダーの持ち方は、SQL Server の実装のときに決める)。誰でも更新できる実装は、そのあとも残す (ユーザーの決定)
- 同じ行を複数の人が同時に直したときの上書きは、検出しない (ユーザーの決定。作業は基本的に 1 人が担当し、同じ行を同時に直す運用が、ほぼ無いため)。行の更新は変えた列だけ書くので、別の列を直した変更は消さない。防ぐ必要が出たときは、表を変えずに、更新の SQL の条件に「更新日時が読んだときと同じ」を足す ([database.md](database.md) の「表の決まり」)

### 表 (ローカルモードの SQLite と、DB モードの SQL Server で同じ)
表の決まり (共通ヘッダー・NULL を使わない・論理削除・外部キーなし)と、型の対応は [database.md](database.md) に従う。型は DB に依存しない言い方で書き、SQL Server と SQLite での型は database.md の「型の対応」を見る。**列ごとの型・既定値・検査・インデックスを書いた表の定義書は、[database.md](database.md) の「列」の「作業管理の表 (6 つ)」**。下の表は、その要約。列は、1 列目の `Id` と共通ヘッダー 5 列のあとに並ぶ。

| 表 | 内容の列 |
| --- | --- |
| `WorkProject` | 案件マスター。`Name`(200)・`Note`(1000) |
| `WorkGroup` | グループ。`ProjectId`・`ParentGroupId`(0 は案件の直下)・`SortOrder`・`Name`(200)・`Note`(1000) |
| `WorkItem` | 作業。`ProjectId`・`GroupId`(0 は案件の直下)・`SortOrder`・`Name`(200)・`Note`(1000)・`PriorityCodeNo`・`StartDate`(ない日は `0001-01-01`)・`DueDate`(ない日は `9999-12-31`)・`StatusCodeNo`・`ProgressCodeNo`・`PlannedHours`(0 は予定なし)・`CompletedOn`(未完了は `9999-12-31`)・`ActualTotalHours`(実績の累計) |
| `WorkRecord` | 日ごとの記録。`ProjectId`・`WorkItemId`・`Date`・`Hours`・`Note`(1000)。`Id` は `bigint` |
| `WorkProjectSelection` | 利用者が表示する案件に選んだ記録。`UserId`・`ProjectId` |
| `CodeMaster` | コードマスタ (状態・進捗度・優先度の選択肢など)。`FeatureNo`・`CategoryNo`・`CodeNo`・`SortOrder`・`NumericValue`・`Name`(100)。「コードマスタ」の節 |

- 時間の列 (`Hours`・`PlannedHours`・`ActualTotalHours`)は、実数 (小数 2 桁)で持つ。SQL Server は `decimal`、SQLite は `REAL`。合計は、書くたびに小数 2 桁へ丸める (`ROUND(SUM(…), 2)`)ので、SQLite の誤差が積み上がらない ([database.md](database.md) の「型の対応」)
- 人は `CreatedByUserId` で表す。日ごとの記録の持ち主 (人ごとに 1 件)は、この列。案件・グループ・作業の作成者は、担当者とは別 (担当者の列は、SQL Server の実装のときに決める)。`WorkProjectSelection` は、`ReminderState` と同じく、`UserId` を持ち、作成者・更新者は `UserId` と同じ人
- **インデックス** (更新日時を含むものは、削除された行も含める。ほかは削除されていない行だけ)
  - `WorkProject`: `(UpdatedAt)`
  - `WorkGroup`: `(ProjectId, UpdatedAt)`(選んだ案件の中身の読み込み・差分)
  - `WorkItem`: `(ProjectId, UpdatedAt)`(同上)・`(ProjectId, CompletedOn)`(案件の完了の計算)
  - `WorkRecord`: `(WorkItemId, Date, CreatedByUserId)` は**一意** (人ごとに 1 件。作業の累計の計算し直しにも使う)・`(ProjectId, Date)`(その日の記録)・`(ProjectId, UpdatedAt)`(差分)
  - `WorkProjectSelection`: `(UserId, ProjectId)` は**一意** (削除されていない行の間だけ)・`(UserId, UpdatedAt)`(差分)
  - `CodeMaster`: `(FeatureNo, CategoryNo, CodeNo)` は**一意** (論理削除された行も含めて)・`(FeatureNo, UpdatedAt)`(機能ごとの読み込み・差分)
- ローカルモードのユーザーは、`Id = 1` の固定値。`AppUser` の表は SQLite に作らず、共通ヘッダーの作成者・更新者の列と `UserId` に 1 を入れる (表の形は、DB モードと同じに保つ)。DB モードでは `AppUser.Id`
- 表の作成スクリプトは、SQLite が `src/Data/MmmTool.Data.Sqlite/Sql/`、SQL Server が `src/Data/MmmTool.Data.SqlServer/Sql/` に、番号つきで足す。ローカルの SQLite は、アプリが起動時に作成と版の更新をする。SQL Server は、アプリが表の有無を調べて知らせるだけ ([database.md](database.md))
- DB の行の型 (`MmmTool.Data` の `WorkItemRow` など。種類ごと)と、アプリの型 (`WorkItem` など)は別にする (リマインダーと同じ。日付なし・予定なしの変換もここで行う)。SQLite と SQL Server で共有する
- コードマスタは、画面から編集しない。直すときは SQL で直す (「コードマスタ」の節)。作業の `PriorityCodeNo`・`StatusCodeNo`・`ProgressCodeNo` の列は、コードマスタのコード番号を指す (外部キーは使わない。存在する番号かどうかは、アプリが検査する)
- 保存した値 (作業の累計)が、手で直した SQL などでずれたときは、管理者が SQL で作り直す (`Sql/` に置く集計の作り直しのスクリプト。記録から計算し直す)。普段は、保存のたびに計算し直すので、使わない

## 実装で仮に決めたこと (ユーザー確認待ち。2026-10-11)
- 実績 (日)は、作業の行も案件・グループの合計も、自分の記録だけ (上の「日ごとの記録」)
- 案件の並びは、画面の木では名前の順 (現在の文化の並び)。選ぶ画面と管理画面は、保存先の並び (名前の順)。完全には一致しない場合がある
- 選ぶ画面と管理画面の 1 回に読む件数は 50、検索は入力が止まって 300 ミリ秒後
- 予定時間の 0 は予定なし (保存先の 0 と同じ。0 を入力しても、予定なしに戻る)
- 案件の完了の計算は、状態が完了でない、または完了日が無い作業を未完了とする (状態が正)。問い合わせは `CompletedOn` と `Status` の両方を見る
- 案件の行の更新日時は、案件の名前・備考の変更、案件をまたぐ移動 (移動元と移動先)で更新する。差分で受け取った案件の行が、持っている行と更新日時が違うときは、その案件の中身を読み直す (自分の変更が戻ってきたときも、読み直す)

## 決定の理由
### WBS とガントチャートを別の画面にする
この画面は、入力して管理する表 (WBS)。ガントチャートは、日付を横に並べて見る別の表示で、操作も表示する内容も違う。1 つの画面に混ぜると、どちらの入力も遅くなる。ガントチャートは、この画面と同じデータを読む別の画面として作る。行の高さを固定にし、日付を行が持つ形にしてあるので、作るときにこの画面を直さなくてよい。

### 段数を固定しない
案件・区分・作業は、決まった 3 段ではなく、案件によって段数が変わる。固定にすると、段が足りない案件で作り直しになる。表の 1 列目を木構造にすれば、段数は自由なまま、1 画面で見える。

### グループと作業の 2 種類に分ける
作業に入力した値 (実績・進捗度など)があるまま、あとから子を足すと、その値を集計に混ぜるのか消すのか、決まりを作るたびに例外が増える。種類で分ければ、グループの値は常に子からの計算、作業の値は常に入力、と 1 通りで済む。種類の変更を設けないのも同じ理由 (変換のときの、実績の行き先の例外をなくす)。

### キー操作でなく、右クリックのメニューで階層を作る
Enter・Tab で行を足したり字下げしたりするのは、Excel のアウトラインの操作で、誤って階層が変わりやすい。メニューは、何が起こるかが文字で見え、行の種類 (グループ・作業)も同じ場所で選べる。追加した行をすぐ入力できる状態にして、追加後の手数を減らす。

### 予定時間は作業ごとの共通の値にする
日ごとに予定を持つと、実績 (日ごと)と意味が重なる。作業全体の見積りとして 1 つだけ持てば、実績の合計との比較と、グループの進捗度の重み付けに使える。

### 変更の履歴と、右のペインを持たない (2026-10-11)
ユーザーの決定。銀行のデータのように、変更の証拠が要る種類のデータではないため、項目ごとの変更前の値は残さない。日ごとの実績と日の備考は、日付をキーに残るので、いつ何をしたかは入力日を動かせば分かる。履歴を持つと、変更の検出・記録の保存 (表)・右のペインの画面が増え、変更前の値を見返す場面に対して、持つ部品が多すぎる。

### 状態・進捗度・優先度は、コードマスタのコード番号で持つ
名前を直す・選択肢を足す・並べ替えるときに、保存済みの作業を書き換えなくて済む (作業の行は番号だけを持つ)。同じ決まり (コード番号を保存し、名前・数値は表から引く)に揃えたので、選択肢が増えても処理が 1 通りで済む。進捗度の % を表の数値に置いたので、10 刻みの固定が要らず、55% のような値も、行を足すだけで選べる。Backlog との対応づけも、数値で行える。機能番号は、機能の名前が変わっても変えない数字にした (文字のキーにすると、名前を直すときに、コードと DB の両方を直すことになる)。

### 全員の分を共有して見る (自分の分だけにしない)
案件・グループは、全員で共有する構造なので、ユーザーで絞らない (案件マスターは全員で共通。画面に出す案件を選ぶのは、見え方の選択で、権限ではない)。実績の累計も、全員の合計。「自分に絞る」は、担当者の列を決めるときに作る (絞り込みの機能)。最初から自分の分だけに絞る前提で作ると、共有に広げるときに、読み込み・集計・表の作り直しになる。

### 列の表示・非表示を、画面の中で切り替える
予定時間や進捗度は、入力が面倒になると使われなくなる。設定ページまで行く操作では、切り替えが続かない。画面の「表示列」ボタンなら、その場で切り替えられる。値は消さないので、戻したときに元に戻る。

### 状態と進捗度を連動させない
Backlog も独立している。「外部レビュー完了」(90)の次の 100 が、状態の完了と一致するとは限らない。連動させると、どちらかを直したときに、もう一方が意図せず変わる。

### 名前は説明だけにし、% は数値から組み立てる
表の名前に「70% (作成完了)」の全文を持つと、数値を直したときに名前の % がずれ、文字列を分解する処理も要る。数値を正とし、名前は「作成完了」だけにして、画面で `{数値}% ({名前})` に組み立てる。書式は区分ごとに決まる (進捗度は % つき、状態・優先度は名前のまま)ので、コード側の区分の定義 (`WorkCodes`)に置く。

### 画面からコードマスタを編集しない (旧: 進捗度のラベルの編集を廃止)
全員に影響し、アプリにユーザー・権限の区別が無い。選択肢を足す・外す・並べ替える操作は、別の管理ツールの責務にする (ユーザー決定 2026-10-11)。ローカルモードにだけ編集の口を残すと、モードによって画面が違い、2 つの経路を保つことになる。

### コードの区分と番号を、表の外 (コード)で台帳にする
状態の「完了」は、完了日・非表示・案件の完了の計算が見分ける必要がある。表のデータだけでは、どの番号が完了かをコードが知らない。そのため、状態・優先度のコード番号は、列挙 (`WorkItemStatus`・`WorkItemPriority`)と同じ値にして固定し、表は名前と表示順を持つ。区分番号・機能番号も、コード側の台帳 (`WorkCodes`・`CodeFeatures`)で決める。

### 優先度・開始日・期限日・予定時間・実績 (累計)を左の固定部分に置く
あまり変えない項目 (優先度・日程・予定時間)と、積み上がった合計は、名前と並べて常に見えるほうが、全体の進み具合を見渡しやすい。毎日触る列 (状態・進捗度・実績 (日)・備考 (日)・備考)は、その右に、途切れずに並べる。

### 毎日入力する列を、背景の色で区別する
「どこに何を入れればよいか」で迷うと、入力が続かない。毎日入力する列だけを色で塗り、あまり変えない項目と区別する。優先度を左に置くのは、緑の列を 1 つの連続した帯にして、区別を分かりやすくするため。説明の文言は、画面を長くするので付けない。

### 完全削除をしない
削除は元に戻せる形 (論理削除)だけにする (ユーザーの決定。ローカルモードも同じ)。削除済みの行は表に残るので、読み込みの条件は、必ず削除されていない行に絞り、インデックスも、削除されていない行だけに付ける。

### 日付は、カレンダーの選択欄で入れる (ユーザーの指示)
最初の実装は文字の入力欄だったが、ユーザーの指示で、`CalendarDatePicker` にした。気をつける点は 2 つ。(1) 選択欄は、日付をクリアする操作を持たない。Delete キー・Backspace キーで消す案は、カレンダーが開いている間はキーが入力欄に届かず効かなかったため、やめた。見えない操作に頼らず、右クリックのメニューの「日付をクリア」にした (押した所の列は `TreeGridView.ContextColumnKey` で分かる)。(2) 表の行は使い回されるので、日付の変更のイベントは、使い回しの差し替えでも起きる。そこで、変更のイベントでは、選ばれた日付を行の今の値と比べ、同じなら何もしない (確定の比較は、文字の入力欄と同じ処理)。

### 保存の契機を、確定の操作だけにする
セルの入力は、フォーカスが外れたとき・Enter で保存する。選択欄の「選択が変わった」や、文字の「変わった」は使わない。表の行を使い回すので、行の差し替えで値が変わるたびに、そのイベントが起き、別の行の値が保存される事故が起きうるため。確定のときは、画面の値を行の今の値と比べ、同じなら何もしない。

### IME の初期状態は、入力スコープで決める
入力欄にフォーカスが入った時点で、入力の仕組み (TSF)が、IME の状態を初期化する。コードで IME をオンにしても、フォーカスが入る処理が終わる前だと、すぐ上書きされる (備考の入力欄で、クリックの一瞬だけオンになってオフに戻った)。入力欄が持つ「入力スコープ」は、その初期化が読む、正式な指定なので、`Hiragana` (日本語)・`Number` (数字)を、欄ごとに宣言する。タイマーで何度も設定し直す方法は、タイミングへの依存なので採らない。実機で効かなかったときは、入力スコープでは足りないということなので、別の仕組みを、設計から検討する。

### 優先度・状態・進捗度は、プルダウンではなく、メニューで選ぶ
プルダウン (ComboBox)は、表の行の中で、クリックの処理の途中で開いても、後から開いても、一覧の項目を選べなかった (一覧が閉じるだけで、選択の変更が届かなかった。原因は特定できなかった)。さらに、行ごとに置くと重く、一覧を開いたときの「くるくる」の疑いにもなった。選択肢は短い一覧なので、クリックで、セルの下にメニュー (今の値にチェック)を出して選ぶ形にした。メニューは、右クリックのメニューで動作が確かめられている。

### セルは、表示と入力を分ける
最初は、全セルに入力欄を常に置いていた。次の 3 つの問題があった。(1) 右クリックでも入力欄にフォーカスが入り、メニューを出すだけなのに、全選択・IME・「×」が一瞬動く (入力欄の標準の動きで、外から止められない)。(2) 1 行に、入力欄・プルダウン・カレンダーが十数個あり、重い (プルダウンを開くと「くるくる」が出る件の疑いにもなった)。(3) 行の使い回しで値が入れ替わるたびに、入力欄の変更のイベントが起き、保存の事故の元になる。そこで、表の標準 (DataGrid や表計算)にならい、普段は文字 (TextBlock)だけを出し、左クリック・キーボードで移ったセルだけが入力欄になる形にした。1 行に、入力欄は高々 1 つになる。行を使い回すときは、入力中の状態を必ず表示用に戻す。

### 入力欄の右クリックで、行のメニューを出す
入力中の欄は、右クリックが入力欄の既定のメニュー (切り取り・コピー・貼り付け)に取られる。行のメニューが主な操作 (追加・移動・削除)なので、入力欄にも行のメニューを付け、入力欄の既定のメニューは出さない。Ctrl+X/C/V は、そのまま使える。

### 保存先を、ローカルも SQLite にして、JSON をやめる (2026-10-11)
日々増える記録 (日ごとの実績)は、1 件を書くたびにファイル全体を書き直す JSON と、相性が悪い。ローカルモードも SQLite にすれば、書き込みは 1 件単位になり、DB モードの SQL Server と、同じ表・同じ読み書きの形で作れる。利用者が入れるものは増えない (SQLite は、パッケージに同梱されるネイティブ DLL。`Lib` に置かれ、発行で読み込めることを確かめた。2026-10-11)。この機能は未リリースで、移すデータが無いので、JSON は残さず置き換える (保存先が 2 つのままで済む)。データの性質で分ける決まりにする。日々増える記録を持つ機能はローカルも DB、設定のように件数が増えないものは JSON のまま (手で読める)。

### 保存するのは、作業の実績の累計だけにして、保存のたびに計算し直す
画面を開くたびに、全員の記録を作業ごとに足すと、規模が大きいほど重くなる。測定 (SQLite・手元・案件 1 万件・作業 150 万件・記録 750 万行の疑似データ)では、累計を読むときに集計すると、20 案件で 46 ミリ秒 (1,000 案件なら約 2 秒)かかった。そこで、作業の累計を保存する。

更新は、差分を足さず、保存のたびに計算し直す (1 つの作業の累計の計算し直しは 1 ミリ秒未満)。差分の足し算は、前のずれが残り続け、画面の値から出した差分だと、同時に書く人の変更を取りこぼす。計算し直す形は、どこで何度実行しても結果が同じで、ずれても次の保存で直る。SQL Server のインデックス付きビューのように、DB に計算を任せる手もあるが、SQLite には無く、仕組みが 2 つになるので使わない。MmmBatch に任せる手もあるが、反映が次の実行まで遅れ、ローカルモードには MmmBatch が無く、止まると全員の合計が古くなるので、保存するトランザクションの中で行う (計算の部品は Core にあるので、MmmBatch で使うこともできる)。

案件・グループの合計は保存しない。選んだ案件の中身はすべて読むので、読んだ作業から足せる。保存する値を増やすと、ずれる場所も増える。測定は SQLite の傾向で、SQL Server の実測ではない。

### 表示する案件を、利用者が選ぶ (2026-10-11)
全案件の中身を読むと、案件が増えるほど重くなる (進行中の案件が 5,000 件なら約 75 万行を、全員が開くたびに読む)。利用者が選んだ案件だけを読めば、案件が増え続けても、読む量は選んだ分で決まる。完了した案件が、勝手に一覧に出てくることもない (見たいときは、選ぶ)。

選びを DB に持つ (`WorkProjectSelection`)理由は、(1) どの PC で開いても、同じ案件が並ぶ、(2) 読むときに INNER JOIN で絞れ、案件の番号を何千個も渡さずに済む、(3) 将来、ユーザーごとの設定を DB に置く方向 ([CLAUDE.md](../../CLAUDE.md)) に合う、の 3 つ。この PC の設定に持つ案は、PC ごとに並ぶ案件が違うので採らない。

案件を、最初は閉じた状態で全件出す案は採らなかった。閉じた案件の行にも合計を出すには、案件の合計を保存して、案件の作業が変わるたびに計算し直す必要があり、保存する値とずれる場所が増えるため。選んだ案件の中身を読む形なら、合計は読んだ作業から足せる。

### 案件を、別の表 (案件マスター)にする
案件は、選ぶ対象で、将来、担当者・リーダーの権限が付き、独自の属性 (顧客・期間など)が増える、独立したもの。グループや作業とは、持つ意味が違う。グループの一種として同じ表に入れると、案件の行が自分の番号を案件の番号 (`ProjectId`)に持つ作りになり、行を作ったあとに番号を直す手順が要る。グループを「最上位」へ動かすと、案件が勝手に増える問題もある。別の表なら、案件の登録・選択・削除が案件マスターに閉じ、グループと作業は、案件の中身として、案件の番号で指す。

### 案件・グループ・作業を、別の表に持つ (ユーザーの決定。2026-10-11)
1 つの表に種類を持たせる方式 (EF Core の TPH)と、種類ごとに表を持つ方式 (TPC)は、どちらも標準的で、性能や整合性は引き分けだった (公式の指針は、型ごとの結合を要する方式 (TPT)でなく、この 2 つを勧める)。ユーザーの好みで、種類ごとに表を分ける。作業の列 (状態・予定など)に本物の値が入り、グループの行に意味のない既定値が入らない。コードの型も、種類ごとに分かれる。

親の列が子の行に重なって届かないよう、読み込みは JOIN で全部をつなげず、表ごとの `SELECT` にして、木はメモリで組み立てる (EF Core の分割クエリと同じ考え方)。グループと作業は、同じ親の下で混ざって並ぶので、並び順 (`SortOrder`)は 2 つの表にまたがる 1 つの数にして、メモリで並べる。番号は表ごとに別の連番なので、行の識別は「種類 + 番号」にする。

### 選ぶ画面はフライアウト、案件の管理はウィンドウにする
選ぶのは、画面を見ながら何度も行う操作で、チェックを入れ外しすると、その場で画面に出入りする。ボタンの下に開き、ほかの操作を止めない小さな画面 (フライアウト)が合う。確認ボタンを持つダイアログは、そのたびに画面をふさぐ。登録・名前の変更・削除は、一覧を検索しながら続けて行い、長くなることもあるので、大きさを変えられるウィンドウにする。ウィンドウを開くボタンは、ページ見出し右に置く (「案件の管理」)。選ぶ画面の中には置かない (見出しに常にあるため)。

### 記録の行にも `ProjectId` を持たせる
全案件の 1 日分の記録を読むと、1 日の記録がすべて届く (10 万人 × 1 日 5 件なら 50 万行)。選んだ案件に絞るには、記録の行にも案件の番号が要る。作業の表との結合でも絞れる (測定では、1.5 万行で 80 ミリ秒。`ProjectId` の列だと 51 ミリ秒)が、差分の取得 (選んだ案件の記録の更新だけ)に、`(ProjectId, 更新日時)` のインデックスが要るため、列に持つ (インデックスが無いと、差分の確認が 674 ミリ秒、あると 0.1 ミリ秒だった)。案件をまたぐ移動では、記録の `ProjectId` も同じトランザクションで直す。

### 他の人の更新の反映は、差分の取得にして、サービスに 1 つ置く
ローカルモードと DB モードで、反映の仕組みを変えると、動きが食い違い、片方でしか見つからない不具合が出る。差分の取得は、どちらの保存先でも同じ問い合わせ (基準の時刻より後に更新された行)で書けるので、サービスに 1 つ置き、保存先の実装は行を返すだけにする。

「3 つの表の最大の更新日時を比べて、変わったら全体を読み直す」形は、多数が使うと、誰かが必ず更新しているので、全員が毎分、全体を読み直すことになるため採らない。差分の取得は、変わった行だけが届く (測定では、変化が 0 件の確認が、1,000 案件で 2 ミリ秒)。番号と更新日時で突き合わせるので、同じ行が重なっても結果は変わらない。時刻は保存先が返した値を使い、少し戻して読むのは、確定前だった更新の取りこぼしを避ける標準の作法 (差分取得の資料でも、重なりを持たせて読み、突き合わせを冪等にするのが定石)。

### 更新できる人の判定を、1 か所に集める
今は誰でも更新できるが、将来は担当者とリーダー的な人だけに絞る (ユーザーの方針)。判定が、画面や保存先に散らばっていると、絞るときに全部を探して直すことになる。更新の入口の 1 か所にまとめれば、実装を足すだけで切り替わる。誰でも更新できる実装は、リーダー的な人が代わりに直せるように残す。

### DB モードを、保存先の差し替えにする
保存先をインターフェース (`IWorkItemRepository`)にし、入力の確認と集計を保存先から切り離してあるので、保存先の実装 (SQLite・SQL Server)を足しても、画面・集計は直さない。
