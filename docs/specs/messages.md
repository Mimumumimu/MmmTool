# メッセージ

人どうしが短いメッセージをやり取りする機能の仕様。宛先は人で、画面は会話ごとのチャット形式にする。表はグループチャットにも対応する形で、画面は 1 対 1 だけを作る。

## 概要

- DB モード (サーバーモード)だけで使う
- 宛先は人。人に送ると、その人が「受け取り先」に指定した送信先へ、通知 (ntfy・Discord・Web 版通知)が届く
- メッセージは、書いた時点で、会話に入っている人が読める。通知の送信は、MmmBatch が別に行う ([mmmbatch.md](mmmbatch.md))
- MmmTool と Web 版は、メッセージと通知の状態を DB に書くだけで、外部へは送らない
- 受け取ったメッセージも、自分が送ったメッセージも、会話で見返せる
- 返信は、返信元のメッセージを指して行う

## 位置づけ

- MmmTool に外部へ接続するコードは入れない
- 画面が書くのは `Message` と `MessageDelivery` の行で、MmmBatch が数秒おきに `MessageDelivery` を読んで通知を送る
  - 表の定義は [database.md](database.md)
  - 送る側は [mmmbatch.md](mmmbatch.md) の「メッセージの送信」
- 通知を送る先の送信先は、メッセージの行にも通知の状態の行にも持たない
  - MmmBatch が、送るときに、受け取る人の受け取り先 (`AppUserSetting`)を読んで、送信先の値を `NotificationChannel` から読む
  - MmmTool の画面も、送信先の値を読まない (値は秘密のため)
- 通知の表に、失敗の理由の列を持たない
  - 理由は MmmBatch のログに残す
  - 経過の記録は、状態を持つ表の役割ではないため

## プロジェクト

| 場所 | 中身 |
| --- | --- |
| `src/NotificationChannels/MmmTool.NotificationChannels.Core` | 機能どうしは参照しないため、どちらの Core にも置かない。リマインダーとメッセージで共有する送信先 (`NotificationChannel`・区分・登録名と値の規則・`INotificationChannelRepository`)と、送信先を受け取り先に指定できる設定の登録口 |
| `src/Users/MmmTool.Users.Core` | ユーザーごとの設定 `AppUserSetting` の型と、保存先のインターフェース。受け取り先は、この設定の 1 行 |
| `src/Plugins/MmmTool.Messages.Core` | 保存先が DB でないとき (ローカルモード)は「使えない」実装を登録し、`IsAvailable` が false になる。持つのは、会話・参加者・メッセージ・通知の状態の型と状態 (`Message`・`MessageDelivery` の状態)・入力の上限 (`MessageLimits`)・保存先のインターフェース (会話と人の一覧の読み出し・差分の取得・メッセージの書き込み・1 対 1 の会話の取得) |
| `src/Plugins/MmmTool.Messages` | `MmmTool.Data*` は参照しない。持つのは、画面 (`Main/`)・端末の控え・DI 登録の入口 (`MessagesPlugin`) |
| `src/Data/MmmTool.Data` / `MmmTool.Data.SqlServer` | 行のクラス・Repository の実装で、他の機能と同じ ([../architecture.md](../architecture.md) の「DB のコードの置き場所」) |

- `NotificationChannel` の登録の画面 (一覧・編集・設定ページの「送信先」)は、リマインダーの機能 (`MmmTool.Reminders`)に置く。移すのは型と Repository のインターフェースだけ。
- 受け取り先の指定は、設定ページの「送信先」の次に、「受け取り先」の節として並べる
  - 節に並べる設定は、登録口に登録されたものを読んで作る。リマインダーの機能は、メッセージの名前を持たない。
  - メッセージは、機能番号 3・区分番号 1 (受け取り先)と、画面に出す名前「メッセージ」を、登録口に登録する
  - 種類が増えたときは、その種類の機能が登録するだけで、節に並ぶ

## 受け取り先

- 1 人につき 1 つだけ指定する。保存は、ユーザーごとの設定 `AppUserSetting` の 1 行で、機能番号 3・区分番号 1・コード番号 1・値が送信先の番号 ([database.md](database.md) の `AppUserSetting`)
  - 指定できるのは、自分が使用者の送信先のどれか 1 つ。ntfy・Discord・Web 版通知のどれでもよい。
  - 複数を指定できる形にしない (1 通の通知が、受け取り先の数だけ送られるため)
- 指定を外すこともできる。外すと、その人は、宛先の一覧に出なくなる。
- 更新したあと、全員が未指定から始まる。受け取り先は、受け取る人が決めるので、自動では入れない。
- 指定した送信先が削除されたときは、未指定と同じに扱う
- 受け取り先が未指定の人には、送れない。会話は開けるが、入力欄は押せず、「受け取り先が未設定です」と出す。
- 書いたあとに受け取り先を外された通知は、送れないので「失敗」になる。メッセージは、会話に残り、本人が読める。
- 指定する場所
  - PC 版: 設定ページの「受け取り先」の節。選んだ操作の直後に保存する
  - Web 版: 設定の画面の「メッセージ」の節 ([web.md](web.md) の「設定 (Web 版)」)
- 送り手が、受け取り先を選ぶ画面や、前回の宛先を覚える設定を持たない (受け取る人が決めるため)

## 会話の形

- 会話 (`MessageConversation`)の種類は 2 つ
  - 1 対 1: 同じ 2 人の組に、会話は 1 つだけ。名前は持たない。自分との会話も 1 対 1 で、参加者は自分 1 人。
  - グループ: 名前を持つ。メンバーが同じで名前の違う会話を、いくつでも作れる。
- 画面は、1 対 1 だけを作る。グループの作成・参加者の操作の画面は作らない。表と読み出しは、グループにも使える形にする。
- 1 通のメッセージ (`Message`)は、1 つの会話に属し、本文と送った人と返信元を持つ
  - タイトルを持たない (会話の形では、件名を付けないため)
  - 返信元は、同じ会話のメッセージだけを指せる。サーバーが確かめ、守れなければ 400 を返す。
- 通知の状態 (`MessageDelivery`)は、1 通を、送った人以外の参加者 1 人に通知する状態を 1 行ずつ持つ。自分との会話は、自分に 1 行。

## 画面

- 入口は、サイドバーのページ「メッセージ」だけ
  - トレイのメニュー「メッセージ送信」は置かない (人の一覧と会話を持つ画面は、1 通を送る小さなウィンドウに収まらないため)
- 画面は、左に会話の一覧、右に会話を並べる
  - PC 版の左の幅は 320 の固定。右は残りの幅を使い、720 で止めて、余った幅は右に空ける。右の欄は、中身の幅ではなく、列の幅で決める。中身で決めると、入力した文字の長さで、欄の幅が変わるため。
  - PC 版の枠の中の色は、送信欄のカードと同じ、標準のカードの色にする。地の色のままだと、枠の中と外の区別がつかないため。左の上の行の「新しい会話」と、右の上の行の会話の題名は、同じ高さにして、下の枠の上端をそろえる。
  - PC 版は、会話の一覧とメッセージの一覧を線だけの枠で囲み、送信欄を背景つきの 1 枚のカードにする。作りは、[cli-assist.md](cli-assist.md) の CLI補助の画面と同じ。入力欄は 3 行分の高さ固定で、超えた分は欄内でスクロールする。
  - PC 版の会話の幅は、720 まで。広いウィンドウでも、横に伸ばさない。メッセージの 1 行が長くなりすぎると、読みにくく、送信ボタンも遠くなるため。
- Web 版 (iPhone のブラウザ)にも、同じ作りの画面がある。作りは [web.md](web.md) の「メッセージ (Web 版)」を見る。「送れる状態」の判定は、MmmTool と Web 版で `MessageDraft` を共有する。

### 人の一覧

- 一覧に出るのは、やり取りのある会話だけ。自分が入っている会話で、1 対 1 の会話は相手の表示名、グループは会話の名前で出す。
  - 並びは、最後のメッセージが新しい順
  - 各行は、名前、最後のメッセージの 1 行目、時刻
  - 会話が 1 つも無いときは、「新しい会話」から宛先を選ぶ案内を出す。
- Web 版だけ、読んでいないメッセージがある会話の行に、名前の左に青い点を付け、名前を太字にする。メールの一覧と同じ形。
  - 読んでいないかどうかは、端末ごとに持つ。DB に既読を記録しない。持ち方と、ホーム画面のアイコンの数字は [web.md](web.md) の「通知 (Web 版)」の、ホーム画面のアイコンの数字を見る。
  - 会話の最後のメッセージが読んでいないときに付ける。会話を開くと、画面に出たメッセージが読んだことになり、印が消える。
  - 上のバーの右の「すべて既読にする」で、メッセージの読んでいない分をすべて外す。読んでいない分が無いときは、押せない。確認は出さない。
  - 未読の印と「すべて既読にする」は、メールの言い方にそろえた。メールの既読と同じく、自分の画面だけの状態で、相手には見えない。
  - PC 版には付けない。PC 版は、通知ダイアログで新着を知らせる。
- 新しい相手へは、一覧の上の「新しい会話」で、宛先に選べる人の一覧を出して選ぶ。名前や文字を入れて探す操作と、探す欄は無い。
  - PC 版: 左の一覧が、宛先に選べる人の一覧に替わる。上の「戻る」で、会話の一覧へ戻る。
  - Web 版: 右下に浮かべた「新しい会話」を押すと、画面全体が宛先を選ぶ画面になる。上の「キャンセル」で閉じる。
  - 出るのは、受け取り先を指定している人だけ。表示名の順で、各行は名前だけ。読む件数は、100 人まで。
  - 自分も出る。自分に送って、通知が届くことを確かめられるため。
  - 1 対 1 の会話がある人も出る。選ぶと、その会話が開く。
  - 開くたびに読み直す
- 人を押すと、その人との 1 対 1 の会話が開く。やり取りがまだ無ければ、空の会話の画面を出し、会話は最初の送信で作る。選んだだけでは、会話を作らない。メッセージの無い会話を、DB に残さないため。
- あとで、この選ぶ画面で複数の人を選べるようにして、グループの作成に広げる。表と読み出しは、グループにも使える形にしてある。
- 最後のメッセージは、会話の表に持たず、メッセージの表から、会話ごとに最新の 1 通を読んで求める

### 会話

- 古いものが上、新しいものが下に並べる。受け取ったメッセージは左、自分が送ったメッセージは右。
- 最初は最新の 50 件を出す。上へスクロールして先頭に近づいたら、さらに古い 50 件を読み足す。読み足しても、見ていた位置は動かさない。
- 1 つのメッセージは、返信元の引用があればその引用、本文、時刻の順
  - 返信元の引用は、返信元を送った人の名前と、本文の 1 行目
- 自分が送ったメッセージには、通知の状態の印を付ける
  - 送信待ちは「送信待ち」、失敗は「失敗」。送信済みには付けない。
  - 印は、通知 (スマホへの知らせ)が届いたかを表す。メッセージが読めるかとは関係しない。
  - 失敗の理由は出さない (理由は MmmBatch のログに残すため)
  - 受け取った人が複数のグループは、送った人以外の通知の状態から、1 つの印を決める。決め方は、グループの画面を作るときに案にして決める。
- 他の人のメッセージは、開いている間、自動で出る ([端末の控えと更新](#端末の控えと更新)を見る)
- 受け取り先が未指定の人との会話も開ける。入力欄は押せず、「受け取り先が未設定です」と出す。

### 入力欄

- 会話の下に置く。本文 (必須)と送信ボタン。返信するときは、入力欄の上に返信元の引用を出す。
  - 本文は最大 1,000 字の複数行
  - 送信ボタン (強調色)は、宛先の人の受け取り先があり、空白だけでない本文があるときだけ押せる
  - PC 版は、本文の欄で Ctrl+Enter を押しても送れる。Enter だけなら改行。送れない状態では、何も起きない。CLI補助の送信と同じ操作にそろえる。
- 返信は、メッセージごとの「返信」を押して始める。押すと、入力欄の上に返信元の引用が出て、「返信をやめる」で取り消せる。
- 本文の最初の入力は、空にする
  - 送った人の署名「○○より」を、本文に入れない。受け取る人には、送った人が、通知の見出しに出るため。[mmmbatch.md](mmmbatch.md) の「メッセージの送信」を見る。
  - 手で書く署名は、書き換えられて、ほかの人の名前で送れてしまう。システムが知っている送った人 (`SenderUserId`)は、偽れない。
- 本文は、フォーカスが来たら IME をオンにする (日本語の入力が多いため)
- 文字数は UTF-16 の 1 単位で数え、上限は DB の列の長さ ([database.md](database.md))と同じ (`MessageLimits`)
- 書けなかったとき (`DataFileException`)は、結果の InfoBar に理由を出す。本文は残す。
- 文言は仮 (人の一覧・入力欄・印・案内の文)

## 会話の読み方

- 会話の 50 件は、`Message` を `ConversationId` で絞り、`Id` の降順で読む。次の 50 件は、読んだ中で一番小さい `Id` より小さい行。
  - ページの番号や件数で区切らない (読んでいる間に新しい行が届いても、同じ行が重ならず、抜けないため)
- 読めるのは、その会話の参加者だけ。参加者かどうかを、サーバーが `MessageConversationMember` で確かめる。
- 並びと区切りは `Id` で決める。共通ヘッダーの `CreatedAt` は、条件や索引に使わない。
- 人の一覧は、自分の `MessageConversationMember` から会話を読み、会話ごとに最新の 1 通を読んで、新しい順に並べる
- 削除された人や送信先との、過去のやり取りも残る。受け取った記録・送った記録のため。

## 1 対 1 の会話の作り方

- 相手との 1 対 1 の会話は、`MessageConversationMember` から探す。自分と相手の両方が参加者で、種類が 1 対 1 の会話。
  - 自分との会話は、参加者が自分 1 人の 1 対 1 の会話
  - 自分と相手の参加者の一覧を比べるときは、会話の数が少ないほうの人から読む
- 見つからなければ、最初の送信のときに、会話を作る。作る処理は、同じ 2 人の組ごとに、DB の鍵 (`sp_getapplock`)で順番に処理する。同時に作っても、1 つだけにするため。
  - 鍵を取ったあとで、もう一度探し、あればそれを使う
  - 鍵は、MmmTool と Web 版が同じコード (`MmmTool.Data.SqlServer`の保存先)を通して使う
- グループには、この検査をしない。メンバーが同じで名前の違うグループを、いくつでも作れるため。

## 端末の控えと更新

サーバーを唯一の正とし、端末の控えは、いつでも作り直せるものにする。

- 会話を開くと、まず端末の控えを出し、そのあと、サーバーに前回からの変更を聞いて、描き直す
  - 新しい端末や、控えが消えた端末は、前回が無いので、サーバーから最新の分をまとめて取る
- 控えは、ログインしている人ごとに分けて持つ。ログアウトとアカウントの変更で、その人の控えを消す。共有の端末で、前の人のメッセージが見えないようにするため。
- 控えは、会話ごとに新しい順の 200 件 (仮)までで、新しいほうから切れ目なく持つ
  - 上へスクロールして取った、それより古いメッセージは、表示するが保存しない
  - 控えは、全部をメモリに読み込まない
- 控えが消えることは、通常の出来事として扱う (iPhone は、ホーム画面のアプリのデータを消すことがあるため)
- 通信できないときは、控えを読むだけで表示し、「最新でない可能性があります」と添える
- 保存先
  - Web 版: ブラウザの IndexedDB。`BrowserClient` と `browser.js` を通す。関数は足すだけにする。
  - PC 版: SQLite の `Cache/MessageCache.db`。消しても作り直されるデータなので、`Cache` に置く。表は [storage.md](storage.md) を見る。
- 前回からの変更は、更新日時 `UpdatedAt` を基準にして取る。仕組みは、作業管理の他の人の更新の反映と同じで、[work-items.md](work-items.md) の「他の人の更新の反映」にある。
  - 基準は、サーバーが返した最大の更新日時。次の確認では、基準から 10 秒 (仮)戻して読む。確定が遅れた書き込みの取りこぼしを避けるため。作業管理の 60 秒より短いのは、確認の間隔が数秒で、60 秒戻すと、毎回、読み直す行が増えすぎるため。メッセージの書き込みは短いので、10 秒で確定が間に合う。
  - 同じ行が何度届いても結果が変わらないよう、番号と更新日時で突き合わせる
  - 取るのは、次の 3 つ。会話の数に関係なく、それぞれ索引 1 回で読む。
    - 自分宛のメッセージの新着と通知の状態の変わり: `MessageDelivery (UserId, UpdatedAt)`
    - 自分が送ったメッセージの変わり: `Message (SenderUserId, UpdatedAt)`
    - 自分が新しく入った会話: `MessageConversationMember (UserId, UpdatedAt)`
  - 通知の状態が変わるとき、MmmBatch は、同じトランザクションで、そのメッセージの `UpdatedAt` も更新する。送った人の画面の印を、メッセージの差分で届けるため。
- メッセージの画面を開いている間の自動更新。人の一覧の画面でも、会話の画面でも、更新の知らせを受ける
  - 新しいメッセージは、「更新」の操作なしで出る
  - Web 版: サーバーが、数秒おきに、更新された行を調べる。全員分を 1 つの問い合わせにして、更新された会話の番号だけを取る。会話を開いている端末に、その会話の更新があることだけを、Server-Sent Events で知らせ、端末は差分を取る。知らせが届かないときは、前面に戻ったときの読み直しで補う。
  - Web 版の間隔は 3 秒 (仮)で、サーバーが DB を調べる間隔
  - PC 版: サーバーを通さず、PC が DB を、場面ごとの間隔で読む。間隔はどれも仮。

    | 場面 | 間隔 |
    | --- | --- |
    | 会話を開いていて、ウィンドウが見えている | 2 秒 |
    | それ以外 (アプリが動いている間) | 10 秒 |

    - 読むのは、どの場面も同じ差分の取得。間隔だけを変える。人の一覧は、読んだ結果から、端末の控えで作り直す。
    - ウィンドウが見えるようになったときと、会話を開いたときは、すぐ読む。ウィンドウが見えているかは、トレイへ隠している間や最小化している間を除いて決める
  - PC 版は、新着を、通知ダイアログ (SDK の `INotificationDialogService`)で知らせる
    - 出すのは、他の人から届いた新着で、いま前面で開いている会話以外のもの。前面で見ている会話の新着は、ダイアログに出さない。
    - 節の送り元のキーは `message`、並びの値は、サイドバーの並びと同じ 5。項目は、送った人の名前と、本文の 1 行目。押すと、その会話を開く。
    - 出すのは、アプリを起動してから届いた新着だけ。アプリを閉じている間に届いたものは、出さない。既読を DB に記録しない。
    - 受け取り先が ntfy や Discord の人も、PC のダイアログが出る。ダイアログは PC のアプリだけのもので、受け取り先とは関係しない。

## 送るときの動き

- 押すと、先に、宛先の人の受け取り先があることを確かめる。無ければ、何も書かず、理由を結果に出す。
- あれば、次を 1 つのトランザクションで書く
  - 相手との 1 対 1 の会話 (なければ作る)に、`Message` の行。送った人は今のユーザー。本文は前後の空白を取る。
  - 送った人以外の参加者ごとに、`MessageDelivery` の行。状態は送信待ち・試した回数は 0。自分との会話は、自分に 1 行。
- 同じ内容を続けて送っても、別の行にする (一意制約を付けない)
  - 1 回の送信の操作が 1 通
- 押した直後にもう一度押されても、2 通送らない
- 書けたら、本文を空に戻す。会話の末尾に、「送信待ち」の印つきで現れる。成功の帯は出さない。
- 通知が届いたかは、印の変わりで分かる。失敗の理由は、MmmBatch のログで見る。
  - MmmBatch が長く止まっていたあとの起動でも、送信待ちの行は古さにかかわらず送る

## DB モードだけ

- `FeatureInfo.AvailableWhen` ([SDK の architecture.md](../../external/MmmSdk/docs/architecture.md))で、メッセージの保存先が使えない (`IsAvailable` が false = ローカルモード)ときは、機能そのものを無いものとして扱う。サイドバー・設定ページの「機能」の一覧のどれにも出ない。
- 機能のオン・オフは既定でオン
  - 設定ファイルに `Feature.Messages.Enabled` が残っていても、ローカルモードでは効かない
  - 詳細は [settings.md](settings.md)
- 設定ページの「送信先」(送信先の登録の画面を開く)も、DB モードのときだけ出す
