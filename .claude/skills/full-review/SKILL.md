# リポジトリ全体の総合レビュー

> **これは写し**。正本はユーザー側の `~/.claude/skills/full-review/SKILL.md`。クラウドセッション（Claude Code on the web）ではローカルのユーザー用スキルを読めないため、このリポジトリに写しを置いている。ルールを直すときは正本を直し、同じ内容をここへ写す（片方だけ直さない）。

リポジトリ全体の構造と全ソースコードをレビューする。単なるバグチェックではなく、次の 4 つの観点から総合的に評価・指摘する。

1. ディレクトリ構造・ファイル配置の妥当性
2. アーキテクチャ・モジュール分割のバランス
3. コードの品質・可読性・設計上の懸念点（リファクタリング提案）
4. セキュリティやパフォーマンス上の注意点

## 前提
- 対象は今の作業ツリーそのもの。git の差分・直近のコミットとの比較は使わない（`git diff` / `git log` で対象を決めない）
- サブモジュールも含めてリポジトリ全体を見る。`bin/` `obj/` `.vs/` `*.g.cs`・同梱の外部ライブラリ（例：`Assets/` 内の minified の js）は読まない（置き方の妥当性だけ見る）
- 引数があれば、その範囲だけを同じ観点で見る（例：`/full-review external/MmmSdk`）

## 進め方

### 0. 始める前に必ず確認する（例外なし）
時間と使用量（トークン）を多く使うので、呼ばれてもすぐには始めない。
- 最初の最初に、ツールを 1 つも呼ぶ前に、次の 1 行だけを出力する（数えるコマンドが動くのを見て、始まったと誤解されないように）
  - 「まず規模をチェックします。レビューをやるかどうかは、そのあとで確認します。」
- 対象のファイル数・行数だけを数える（`bin/` `obj/` 等は除く。ファイルの中身はまだ読まない）
- 下の「分け方」で読む単位を決める
- 次をユーザーに伝え、AskUserQuestion で実行してよいかを聞く
  - 対象の範囲と、ファイル数・行数
  - 読む単位の一覧（単位ごとのファイル数・行数）
  - 時間と使用量を多く使うこと（5 時間の利用制限の残りが少ないときは、リセット後をすすめる）
- 選択肢：「実行する」（おすすめ）/「範囲を絞る」（範囲を聞いてから、もう一度この確認をする）/「やめる」
- 「実行する」が選ばれるまで、下の手順に進まない

### 1. 全体を把握する（自分で行う）
- リポジトリのツリー（フォルダ・ファイルの一覧と行数）を出す
- ソリューション・プロジェクトの構成と参照関係、使っているパッケージ、ビルド設定（`Directory.Build.props` 等）を読む
- `README.md` と `CLAUDE.md`（リポジトリ直下・サブモジュール・`~/.claude/CLAUDE.md`）と、CLAUDE.md が読み込みを指示しているスキルを読む。そこに書かれた方針・決定事項は評価の前提にする（意図的な判断を知らずに指摘しないため。ただし判断そのものに異論があれば、理由をつけて提案として出してよい）
- ここで観点 1・2 の見立て（構造・分割の全体像）を作る

### 2. 全ソースコードを読む
- 全ファイルを最後まで読む。量が多くて 1 人で読み切れないときは、Agent ツール（`general-purpose`）で、下の「分け方」の単位ごとに並行で読ませる
- 分け方：プロジェクト（csproj）ごとに 1 単位。それ以外の分け方・まとめ方はしない（大きいプロジェクトもフォルダで分けない、小さいプロジェクト同士もまとめない）。単位の名前はプロジェクト名
- csproj に属さないファイル（リポジトリ直下の設定・ドキュメント等）は、手順 1・3 で自分で見る
- 分けて読ませるときの依頼は次の形にする（コードは変更させない）

```
次の範囲のソースコードを全部、最後まで読んでください。コードは変更しないでください。
範囲: <フォルダ・ファイルの一覧>
前提として読むもの: <README・CLAUDE.md・スキルの一覧>

リポジトリ全体の総合レビューの一部です。次の 4 つの観点で、この範囲について気づいたことを報告してください。
1. ディレクトリ構造・ファイル配置の妥当性
2. アーキテクチャ・モジュール分割のバランス（この範囲の責務・依存・大きさ）
3. コードの品質・可読性・設計上の懸念点（リファクタリング提案）
4. セキュリティやパフォーマンス上の注意点

- 置き場所の候補も挙げる：この範囲の型・ファイルのうち、別のプロジェクトにあるべきもの（UI に依存しないので Core へ・アプリ固有でないので SDK へ・逆に SDK や Core にあるのにアプリ固有・UI 依存のもの）を、理由つきで
- 推測では書かない。該当のコードを `ファイル:行` で示し、なぜそう言えるかを説明する
- 良い点も短く書く（評価のため）
- 出力は日本語。観点ごとに、指摘（場所・内容・理由・提案）と良い点を並べる
```

### 3. まとめて評価する（自分で行う）
- 範囲ごとの報告をつなぎ、リポジトリ全体として評価し直す。範囲をまたぐ問題（依存の向き・重複した仕組み・層の偏り・ドキュメントとコードの食い違い）はここで見る
- 全体構成の点検（プロジェクトごとのレビューでは見えないので、必ず自分で行う）：
  - 置き場所：各プロジェクトの型を一覧にし、それぞれが正しいプロジェクトにあるかを決める。基準は、UI・Windows に依存しない処理 → Core（アプリ）、どのアプリでも使える汎用の部品 → SDK、アプリ固有の画面・機能 → アプリ。SDK の Core / WinUI の分け方も同じ基準で見る。レビュー役が挙げた「置き場所の候補」もここで確かめて採否を決める
  - 依存の向き：プロジェクト参照が「アプリ → Core → SDK.Core」「アプリ → SDK.WinUI → SDK.Core」の向きだけか、SDK がアプリを知っていないか、Core が UI を参照していないか
  - 重複：同じ役目の仕組みが複数のプロジェクトにないか（SDK にあるのにアプリで作り直している等）
  - 粒度：プロジェクトの大きさ・数が釣り合っているか（分けすぎ・まとめすぎ）
  - 結果は観点 1・2 の指摘として、移す先と理由を書く
- 重要な指摘は、自分で該当のコードを読み直して確かめる。確かめられなかったものは「要確認」と書く
- 同じ指摘はまとめる

### 4. 報告する
チャットに出し、同じ内容を `_local/reviews/review-yyyyMMdd-HHmm.md` にも保存する（`_local/` が無い・git の管理対象なら保存しない）。

1. 総評：全体の評価を数行（強み・いちばんの課題）
2. 観点ごとの評価（1〜4 の順）
   - 評価（良い / おおむね良い / 課題あり）と、その理由
   - 指摘の一覧。1 件ずつ：番号（例：`S-01` 構造 / `A-01` アーキテクチャ / `Q-01` 品質 / `P-01` セキュリティ・パフォーマンス）・重要度（高 / 中 / 低）・場所（`ファイル:行` またはフォルダ）・内容・理由・提案（複数あるならおすすめを先頭に、理由つき）
3. 優先して取り組むとよいもの（上位 3〜5 件）

報告したら止まり、どれに取り組むかを聞く。

### 5. 直す（確認を取ってから）
- 選ばれた指摘だけに取り組む。構成の変更・動作が変わる変更は、始める前に内容を説明して確認を取る
- サブモジュールの SDK を先に直してから、アプリを直す
- 変更は小さな単位で行い、そのたびにビルドが通ることを確かめる
- コミット・push はしない（ユーザーの指示があるまで）。説明が変わったら CLAUDE.md・README も直す
